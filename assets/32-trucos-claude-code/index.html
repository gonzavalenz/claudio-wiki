01

CLAUDE.md

Archivo markdown que Claude Code lee al arrancar cada sesión, con instrucciones persistentes sobre tu proyecto: convenciones, comandos, arquitectura.

 Básico ▸

Cuándo usarlo

Cuando Claude comete el mismo error dos veces, cuando escribís la misma corrección en el chat que ya escribiste la sesión pasada, o cuando un compañero nuevo necesitaría el mismo contexto para ser productivo.

Cómo

Se puede crear a mano en ./CLAUDE.md o ./.claude/CLAUDE.md, o generarlo a partir del código con /init (Claude explora el repo y arma un borrador). Mantenelo corto: la documentación oficial recomienda menos de 200 líneas, porque un archivo más largo consume más contexto en cada turno y baja la adherencia a las reglas.

Ejemplo

Un CLAUDE.md típico en un repo de dbt + Airflow:

# Proyecto: pipeline de ventas

- Correr `dbt build --select state:modified+` antes de commitear cambios en models/
- Los modelos de staging usan prefijo `stg_`, nunca `raw_`
- BigQuery: el dataset de desarrollo es `analytics_dev`.
  No tocar `analytics_prod` sin confirmación explícita.
- Los DAGs de Airflow viven en `dags/`, un archivo por pipeline
- Test de un DAG en local: `airflow dags test ventas_diario 2026-08-01`

Detalle que la mayoría se pierde

CLAUDE.md se inyecta como un mensaje más después del system prompt, no como configuración forzada: Claude puede no seguirlo al pie de la letra si la instrucción es vaga o contradice otra. Para reglas que tienen que cumplirse sí o sí (por ejemplo, "nunca corras DROP TABLE sin preguntar") no alcanza con escribirlo acá — hace falta un hook que bloquee la acción de verdad.

Relacionado: CLAUDE.md vivo · vínculos dinámicos · memoria persistente

02

Barra de estado

Una fila configurable al pie de la terminal que corre un script tuyo y muestra lo que ese script imprima: contexto usado, costo, git, lo que quieras.

 Básico ▸

Cuándo usarlo

Cuando querés ver de un vistazo cuánto contexto o costo llevás gastado, sin tener que acordarte de correr /context o /usage cada dos minutos.

Cómo

Lo más simple es pedírselo a Claude en lenguaje natural con el comando /statusline, que genera el script y lo engancha solo en tu configuración:

/statusline mostrame el modelo, el directorio y el % de contexto usado con una barra de progreso

También se puede configurar a mano agregando el campo statusLine en ~/.claude/settings.json, apuntando a un script que lea JSON por stdin.

Ejemplo

Un statusline que muestra la rama de git y el % de contexto es útil cuando estás iterando sobre un DAG de Airflow largo y necesitás decidir si conviene compactar antes de seguir, sin cortar el hilo para preguntarlo.

Detalle que la mayoría se pierde

El statusline corre localmente y no consume tokens de la API. Pero si el script hace git status o git diff en un repo grande, cada actualización puede colgar la interfaz un instante — la documentación oficial recomienda cachear esos comandos usando el session_id que viene en el JSON, con un TTL de unos segundos.

Relacionado: monitoreo de contexto

03

Esfuerzo y modelo

/model elige qué modelo responde; /effort elige cuánto "piensa" antes de responder. Dos perillas distintas para ajustar costo contra calidad.

 Básico ▸

Cuándo usarlo

Bajá el esfuerzo para tareas mecánicas y repetitivas (armar el boilerplate de un modelo de dbt nuevo). Subilo para debug difícil (una query de BigQuery que devuelve resultados que no cierran, un DAG que falla intermitente).

Cómo

/effort low
/effort high
/effort xhigh
/model opus

El cambio de esfuerzo aplica de inmediato, sin esperar a que termine la respuesta actual. Los niveles disponibles son low, medium, high, xhigh y max (la disponibilidad depende del modelo).

Ejemplo

/effort xhigh antes de pedirle que revise por qué una tabla particionada por fecha y clusterizada por customer_id en BigQuery sigue escaneando de más — ahí vale la pena que piense más antes de proponer un fix.

Detalle que la mayoría se pierde

Effort más alto significa más tokens de "pensamiento" antes de la respuesta, y eso se traduce en más costo y más latencia — no es gratis dejarlo siempre al máximo. Además, no todos los modelos exponen todos los niveles: por ejemplo, ultracode se reporta como xhigh en el statusline aunque internamente sea otra cosa.

04

Contexto corto

No es un comando, es un hábito: mantener la conversación enfocada en la tarea actual en vez de dejar que se acumule historial de exploraciones viejas.

 Básico ▸

Cuándo usarlo

Cuando arrancás una tarea nueva que no depende de lo que charlaste antes, o cuando notás que las respuestas empiezan a divagar o repetir cosas que ya se resolvieron.

Cómo

Usá /clear entre tareas no relacionadas en vez de arrastrar todo en una sesión maratónica. Para exploración ruidosa —leer cientos de logs de una DAG, grepear un dataset grande de código— delegala a un subagente, que trabaja en su propia ventana de contexto y te devuelve sólo el resumen.

Ejemplo

En vez de pedir en la conversación principal "leé los últimos 500 logs de la DAG de ventas y decime qué tasks fallaron", pedile a un subagente que lo haga y traiga sólo la lista de tasks fallidas con la causa — vos seguís trabajando con el contexto limpio.

Detalle que la mayoría se pierde

Más contexto no es gratis: cada token que arrastrás se vuelve a mandar en cada turno (con cache, pero no gratis) y se cobra. Un contexto lleno de ruido tampoco es sólo un tema de costo — empeora la calidad de las respuestas porque Claude tiene que priorizar entre señal y ruido.

Relacionado: monitoreo de contexto · compactación · subagentes

05

Monitoreo de contexto

/context muestra una grilla de colores con qué está ocupando tu ventana de contexto: system prompt, memoria, archivos leídos, conversación.

 Básico ▸

Cuándo usarlo

Antes de arrancar una tarea larga, o cuando sospechás que algo infló el contexto sin que te dieras cuenta (por ejemplo, después de que Claude leyó un archivo de configuración enorme).

Cómo

/context
/context all

/context all expande el detalle por ítem, útil en modo fullscreen donde por default aparece colapsado.

Ejemplo

Correr /context después de que un subagente devolvió el resultado de escanear todos los modelos de un proyecto dbt, para confirmar que el resumen no infló tu contexto principal más de lo esperado.

Detalle que la mayoría se pierde

El porcentaje que muestra /context puede diferir levemente del que ves en el statusline, porque se calculan en momentos distintos del ciclo de la conversación — una pequeña discrepancia entre los dos no es un bug.

Relacionado: barra de estado · contexto corto

06

Compactación

/compact resume toda la conversación para liberar contexto. Para resumir sólo una parte, la herramienta correcta es /rewind, no /compact.

 Básico ▸

Cuándo usarlo

/compact, cuando el contexto está lleno y necesitás seguir trabajando en la misma sesión. La variante selectiva, cuando sólo una parte puntual de la conversación (una exploración larga que ya no aporta) es la que sobra.

Cómo

/compact enfocate en las decisiones sobre el esquema de BigQuery, descartá el resto

/compact acepta instrucciones opcionales para orientar el resumen, pero compacta toda la conversación de punta a punta — no un rango. Para lo selectivo, abrí el menú de rebobinado (/rewind o doble Esc) y elegí "Summarize from here" (resume desde ese punto hacia adelante) o "Summarize up to here" (resume todo lo anterior a ese punto, dejando el resto intacto).

Ejemplo

Pasaste 40 minutos debuggeando por qué un DAG de Airflow no dispara un trigger, encontraste la causa, y ahora arrancás a escribir el fix. Con /rewind → "Summarize up to here" en el mensaje donde encontraste la causa, comprimís todo el ida y vuelta de debugging pero mantenés intacta la conversación de acá en adelante.

Detalle que la mayoría se pierde

Las reglas de CLAUDE.md, skills y memoria sobreviven a /compact — no hace falta repetirlas. El CLAUDE.md de la raíz del proyecto además se vuelve a leer del disco después de compactar; los CLAUDE.md de subcarpetas y las reglas con paths: no se reinyectan solas, recién vuelven a cargar cuando Claude lee un archivo que matchea.

Relacionado: rebobinar · monitoreo de contexto

07

Modo Plan

Un modo en el que Claude puede leer e investigar, pero no editar archivos ni correr comandos con efectos secundarios, hasta que aprobás un plan.

 Básico ▸

Cuándo usarlo

Antes de cualquier cambio con blast radius grande: una migración de esquema en BigQuery, un refactor de un DAG que corre en producción, cualquier cosa donde preferís ver el plan antes de que Claude toque algo.

Cómo

Shift+Tab cicla al modo plan (también /plan). Claude investiga, te presenta un plan, y vos lo aprobás, lo corregís o lo rechazás antes de que se ejecute cualquier edición.

Ejemplo

Pedirle "migrá el modelo stg_orders de materialización incremental a particionado por fecha de evento" en modo plan primero, para ver qué archivos de dbt va a tocar y cómo antes de que lo haga de verdad.

Detalle que la mayoría se pierde

El modo plan no es una caja de arena total: Claude puede seguir corriendo comandos de sólo lectura (grep, bash de consulta, lectura de archivos) sin pedir permiso mientras investiga. Lo que bloquea son las ediciones de archivos y los comandos que cambian estado.

08

Salida temprana

Esc interrumpe a Claude a mitad de una respuesta o de una ejecución de herramienta.

 Básico ▸

Cuándo usarlo

En cuanto ves que se fue por las ramas — por ejemplo, arrancó a tocar archivos de otro dataset que no le pediste, o está por correr un comando más amplio de lo que querías.

Cómo

Esc mientras está generando texto o ejecutando una herramienta.

Ejemplo

Lo interrumpís apenas ves que, en vez de dbt run --select stg_orders, está por correr dbt run a secas sobre todo el proyecto en tu entorno de desarrollo.

Detalle que la mayoría se pierde

Esc corta la respuesta actual, no deshace lo que ya se ejecutó. Si Claude ya escribió un archivo o corrió un comando de bash antes de que lo frenaras, eso ya pasó — para deshacer ediciones de archivos hecho por Claude usá /rewind; los cambios hechos por comandos de bash (como un rm o un UPDATE) no se pueden deshacer desde ahí.

Relacionado: rebobinar

09

Capturas de pantalla

Adjuntar una imagen al prompt para que Claude la analice, en vez de describir con palabras algo que se ve mejor.

 Básico ▸

Cuándo usarlo

Cuando el problema está en una interfaz visual: un dashboard de Looker Studio que renderiza mal, el grafo de una DAG en la UI de Airflow con tasks en rojo, un gráfico de calidad de datos que no cierra.

Cómo

En iTerm2, arrastrá el archivo de imagen directo a la ventana de la terminal, o pegalo con Cmd+V si lo copiaste al portapapeles.

Ejemplo

Pegar un screenshot del grafo de una DAG en la UI de Airflow con varias tasks fallidas en rojo y pedirle "mirá cuáles fallaron y proponeme un fix para la política de retry de esa task".

Detalle que la mayoría se pierde

El pegado con Cmd+V depende de si la imagen quedó en el portapapeles como archivo o como bitmap, y varía entre versiones de terminal. Si el pegado falla, arrastrar el archivo de imagen directo a la ventana funciona siempre como alternativa.

10

Entrada de voz

Dictado por voz activado con /voice: hablás y la transcripción se inserta en vivo en el prompt, en lugar de tipear.

 Básico ▸

Cuándo usarlo

Cuando es más rápido explicar en voz alta un problema largo que escribirlo, o cuando estás lejos del teclado pero cerca del micrófono.

Cómo

/voice        # activa modo hold-to-record (default): mantenés Space apretado para grabar
/voice tap    # modo tap-to-record: un toque arranca, otro toque manda
/voice off    # desactiva

La primera vez que lo activás, macOS te va a pedir permiso de micrófono para tu terminal (System Settings → Privacy & Security → Microphone).

Ejemplo

Mantener Space apretado para explicar en voz alta "che, la task de extracción de Airflow está fallando después del deploy de ayer, revisá qué cambió en el operator de BigQuery" mientras seguís mirando los logs en otra ventana.

Detalle que la mayoría se pierde

Necesita cuenta de claude.ai — no funciona autenticado sólo con API key, Bedrock, Vertex AI o Microsoft Foundry. Tampoco funciona en entornos remotos (SSH, Claude Code en la web) porque el audio se captura en la máquina local. El audio se manda a los servidores de Anthropic para transcribir, no se procesa local, y no consume tokens ni cuenta contra los límites de /usage.

Ojo con la fuente original: la lista de la que salió este truco decía que "no es un comando /voice". Es al revés: /voice es el comando que lo activa; lo que varía es el modo (hold o tap), no si existe el comando.
11

Preguntas proactivas

Pedirle explícitamente a Claude que pregunte antes de tomar decisiones ambiguas o ejecutar algo riesgoso, en vez de asumir y seguir.

 Básico ▸

Cuándo usarlo

En tareas donde una decisión mal tomada es cara de revertir: un cambio de esquema en una tabla productiva, un borrado de partición en BigQuery, un cambio en la lógica de un DAG que corre a las 3am sin que nadie lo mire.

Cómo

Instrucción puntual en el prompt, o una línea en CLAUDE.md:

# En CLAUDE.md
- Si vas a borrar o modificar datos en BigQuery, mostrame la query
  y esperá confirmación antes de ejecutarla.
- Si una tarea se puede interpretar de más de una forma, preguntame
  en vez de asumir cuál.

Ejemplo

"Antes de correr el DELETE sobre la tabla de staging, mostrame la condición del WHERE y esperá que te confirme."

Detalle que la mayoría se pierde

Esto es una instrucción de comportamiento, no una traba técnica: Claude puede igual no preguntar si el CLAUDE.md es ambiguo o si compite con otra instrucción. Para bloquear de verdad una acción (no simplemente pedirle que avise) hace falta un hook PreToolUse con un matcher sobre Bash, que sí corre siempre sin depender de que el modelo se acuerde.

Relacionado: hooks productivos

Nivel intermedio

Una vez que el uso diario ya es fluido: delegar trabajo, empaquetar conocimiento repetible y mantener el setup al día.

12

Subagentes

Asistentes especializados que corren en su propia ventana de contexto, con su propio system prompt y permisos, y devuelven sólo el resultado.

 Intermedio ▸

Cuándo usarlo

Cuando una tarea secundaria inundaría tu conversación principal con resultados de búsqueda, logs o contenido de archivos que no vas a volver a necesitar. También cuando repetís siempre el mismo tipo de encargo con las mismas instrucciones.

Cómo

Un subagente es un archivo markdown con frontmatter YAML en .claude/agents/ (proyecto) o ~/.claude/agents/ (usuario, todos tus proyectos):

---
name: log-triager
description: Revisa logs de tasks fallidas de Airflow y devuelve un resumen accionable. Usar proactivamente cuando una DAG falla.
tools: Read, Bash, Grep
model: haiku
---

Sos un triager de logs de Airflow. Cuando te pasen el nombre de una DAG
y una fecha de ejecución, buscá los logs de las tasks fallidas,
identificá la causa raíz y devolvé un resumen de máximo 10 líneas
con: task, causa probable, y si es reintentable.

Se invoca automáticamente cuando Claude cree que aplica, con lenguaje natural ("usá el subagente log-triager"), o con @ para forzar cuál corre (@agent-log-triager).

Ejemplo

Un subagente bq-cost-checker con acceso sólo a Bash restringido a bq query --dry_run, que estimás el costo de una query antes de correrla sobre una tabla de ventas de varios TB.

Detalle que la mayoría se pierde

Cada subagente arranca con contexto fresco: no ve tu conversación previa ni los archivos que ya leíste (la excepción es un subagente en modo fork, que sí hereda la conversación). Además, el rewind no restaura ediciones hechas por un subagente, salvo que corra en foreground como fork — si un subagente rompe algo, tenés que revertirlo con git, no con /rewind.

Relacionado: contexto corto · worktrees

13

Skills personalizadas

Recetas para tareas repetitivas: instrucciones que Claude carga sólo cuando hacen falta, en vez de vivir siempre en el contexto como CLAUDE.md.

 Intermedio ▸

Cuándo usarlo

Cuando venís pegando las mismas instrucciones en el chat una y otra vez, o cuando una sección de tu CLAUDE.md creció hasta convertirse en un procedimiento de varios pasos en vez de un dato simple.

Cómo

Un archivo SKILL.md dentro de una carpeta con el nombre de la skill:

# .claude/skills/nueva-tabla-bq/SKILL.md
---
name: nueva-tabla-bq
description: Crea una tabla nueva en BigQuery con partición, clustering y el modelo de dbt correspondiente. Usar cuando se pide agregar una tabla nueva al warehouse.
---

1. Preguntá el nombre de la tabla, la columna de partición y las columnas de clustering.
2. Generá el modelo de dbt en models/marts/ con el bloque `config` correspondiente.
3. Agregá el test de `not_null` y `unique` sobre la primary key.
4. Corré `dbt run --select  --target dev` para validar antes de terminar.

El nombre de la carpeta se convierte en el comando: esta skill se invoca con /nueva-tabla-bq. Para generarlas con ayuda, existe el plugin oficial skill-creator:

/plugin marketplace add anthropics/claude-plugins-official
/plugin install skill-creator@claude-plugins-official

Ejemplo

Una skill revisar-dag que, antes de mergear un DAG nuevo, chequea que tenga retries, on_failure_callback configurado y que no use schedule_interval deprecado en favor de schedule.

Detalle que la mayoría se pierde

A diferencia de CLAUDE.md, el cuerpo de una skill sólo se carga en contexto cuando se usa — podés tener documentación de referencia larga ahí adentro casi gratis. Los comandos personalizados viejos en .claude/commands/ siguen funcionando igual, pero las skills son la forma recomendada porque suman carpeta de soporte, control de quién la invoca y ejecución en subagente.

Relacionado: actualizar skills · CLAUDE.md · subagentes

14

Actualización de skills

Refinar una skill no es sólo editar el texto: es medir si dispara cuando debe y si el resultado mejora cuando dispara, antes y después del cambio.

 Intermedio ▸

Cuándo usarlo

Cuando una skill dispara en prompts donde no debería, no dispara cuando sí debería, o cambiaste las instrucciones y no estás seguro de si mejoró algo o sólo lo movió de lugar.

Cómo

La forma manual es comparar en dos sesiones frescas: correr los mismos prompts con la skill habilitada y con la skill deshabilitada, y ver la diferencia. El plugin oficial skill-creator automatiza ese loop:

evaluate my nueva-tabla-bq skill with skill-creator

A partir de ahí te guía para escribir casos de prueba (guardados en evals/evals.json dentro de la carpeta de la skill), corre cada caso en un subagente con contexto limpio, compara con-skill contra sin-skill, y hace una comparación ciega A/B entre dos versiones de la skill antes de que decidas cuál dejar.

Ejemplo

Después de agregarle un paso nuevo a la skill revisar-dag, correr la evaluación A/B contra la versión anterior con 5 DAGs reales del repo como casos de prueba, para confirmar que el paso nuevo no rompió la detección de los casos que ya andaban bien.

Detalle que la mayoría se pierde

Ver que una skill "se activó" no dice si hizo lo que querías — sólo dice que Claude la encontró. Hay que medir las dos cosas por separado: si dispara en los prompts correctos, y si el resultado cuando dispara es el esperado. El plugin también genera prompts que deberían y no deberían disparar la skill, para ajustar la description si se activa de más o de menos.

Relacionado: skills personalizadas

15

CLAUDE.md vivo

Tratar el CLAUDE.md como un documento que se actualiza al final de cada sesión con lo que se aprendió, no como algo que se escribe una vez y se olvida.

 Intermedio ▸

Cuándo usarlo

Al cierre de una sesión donde corregiste a Claude más de una vez sobre lo mismo, o donde descubriste una convención del proyecto que no estaba documentada.

Cómo

Antes de terminar: revisá si algo de lo que corregí hoy debería
quedar en CLAUDE.md (no en la memoria automática), y proponeme
la línea exacta para agregar.

Ejemplo

Después de corregir dos veces en la misma sesión que los tests de dbt van con --target dev y no con el target por default, cerrar pidiendo que agregue esa regla a CLAUDE.md para no tener que repetirla la próxima vez.

Detalle que la mayoría se pierde

Esto se solapa con la memoria automática, que hace justamente esto sin que se lo pidas. La diferencia es de audiencia y control: CLAUDE.md lo escribís vos, va a git y lo ve todo el equipo; la memoria automática la escribe Claude, es local a tu máquina y no la revisa nadie más. Usá CLAUDE.md para lo que el equipo necesita saber, y dejá que la memoria automática junte tus propias costumbres.

Relacionado: CLAUDE.md · memoria persistente

16

Vínculos dinámicos

CLAUDE.md puede importar otros archivos con @ruta/archivo.md en vez de que todo viva apilado en un solo archivo gigante.

 Intermedio ▸

Cuándo usarlo

Cuando tu CLAUDE.md empieza a mezclar temas distintos (convenciones de dbt, reglas de Airflow, estilo de Python) y conviene separarlos en archivos con nombre propio, o cuando ya tenés un AGENTS.md u otro archivo de instrucciones que no querés duplicar.

Cómo

# CLAUDE.md
Ver @docs/convenciones-dbt.md para el estilo de modelos.
Ver @docs/convenciones-airflow.md para el estilo de DAGs.

@AGENTS.md

Rutas relativas o absolutas, con hasta 4 niveles de imports recursivos. El parser ignora lo que está entre backticks o en bloques de código, así que `@README` entre comillas no se importa, escrito suelto sí.

Ejemplo

Separar docs/convenciones-bigquery.md (naming de datasets, política de particionado) de docs/convenciones-airflow.md (estructura de DAGs, manejo de retries), e importar ambos desde el CLAUDE.md principal.

Detalle que la mayoría se pierde

Los imports no ahorran contexto: se expanden y se cargan enteros al arrancar la sesión, igual que si estuvieran pegados en el CLAUDE.md. Sirven para organizar, no para aligerar — si el objetivo es que algo cargue sólo cuando hace falta, eso es una skill, no un import. Además, un import que apunta fuera de tu carpeta de trabajo (por ejemplo a tu $HOME) dispara un diálogo de aprobación la primera vez, como protección contra archivos que otra persona haya comiteado.

Relacionado: CLAUDE.md · skills personalizadas

17

Árbol de archivos

Pegar la salida de tree en CLAUDE.md para que Claude "vea" la estructura del proyecto de entrada.

 Intermedio ▸

Cuándo usarlo

Con matices: sirve como ayuda puntual de onboarding (una sesión nueva, un repo grande donde perderse es fácil), no como entrada permanente de CLAUDE.md.

Cómo

tree -L 2 -I 'venv|__pycache__|.dbt|target|logs' models/ dags/

Si igual lo querés fijo en CLAUDE.md, limitalo a 1-2 niveles de profundidad y a las carpetas que realmente cambian de significado según dónde estás (no listes cada archivo .sql).

Ejemplo

Un árbol de dos niveles mostrando models/staging/, models/intermediate/ y models/marts/ le da a Claude el criterio de capas de dbt sin listar los 200 archivos .sql de adentro.

Detalle que la mayoría se pierde

Un árbol estático en CLAUDE.md consume contexto en cada turno de cada sesión, y se desactualiza apenas alguien agrega o borra un archivo — nadie se acuerda de regenerarlo. Además, Claude ya puede explorar la estructura real con sus propias herramientas (Glob, ls) cuando la necesita, así que en la mayoría de los proyectos un árbol fijo es puro costo sin beneficio. Vale la pena sólo cuando la estructura por sí sola comunica una convención que no es obvia mirando un archivo suelto.

Relacionado: CLAUDE.md

18

Rebobinar

/rewind (o doble Esc con el prompt vacío) abre un menú para volver código y/o conversación a un punto anterior de la sesión.

 Intermedio ▸

Cuándo usarlo

Cuando un cambio salió mal y querés volver al estado anterior sin usar git a mano, cuando querés probar un enfoque alternativo sin perder el punto de partida, o cuando la conversación se llenó de un debugging largo que ya no aporta.

Cómo

/rewind, o doble Esc con el input vacío (si el input tiene texto, doble Esc lo borra en vez de abrir el menú — el texto borrado queda en el historial, ↑ lo recupera). El menú lista cada prompt de la sesión y ofrece:

  • Restore code and conversation: vuelve ambos a ese punto
  • Restore conversation: rebobina la charla, deja el código como está ahora
  • Restore code: revierte los archivos, deja la conversación como está
  • Summarize from here / up to here: comprime la conversación desde o hasta ese punto (ver compactación)

Ejemplo

Probaste que Claude reescriba un modelo de dbt de incremental a table completa, no te convenció el resultado, y con "Restore code" volvés los archivos al estado de antes del intento sin tocar la conversación donde ya explicaste el contexto.

Detalle que la mayoría se pierde

Lo que no restaura: cambios hechos por comandos de bash (rm, mv, un UPDATE en la base) — sólo rastrea ediciones hechas con las herramientas de archivo de Claude. Tampoco restaura ediciones de subagentes (salvo un fork en foreground), ni archivos symlinkeados o hardlinkeados, ni cambios externos hechos fuera de la sesión. No es un reemplazo de git: los checkpoints se borran a los 30 días por default.

Relacionado: compactación · salida temprana

Elección de interfaz

La CLI en la terminal es la superficie más potente y rápida para trabajar con Claude Code, por encima de otras integraciones.

 Intermedio ▸

Cuándo usarlo

Para el trabajo del día a día: correr comandos de bq, dbt y airflow en la misma terminal donde ya trabajás es más directo que saltar a una extensión de IDE o una interfaz web para cada cosa.

Cómo

iTerm2 (o Terminal.app) más el CLI de Claude Code instalado. Las extensiones de VS Code y JetBrains están buenas para ver diffs con contexto de archivo, pero para el flujo agéntico completo (permisos, subagentes, hooks, worktrees) la CLI expone todo primero.

Ejemplo

Tener una pestaña de iTerm2 con Claude Code corriendo en el repo de dbt, y otra con airflow standalone levantado para probar los DAGs en caliente mientras Claude edita — sin cambiar de aplicación.

Detalle que la mayoría se pierde

No es una regla absoluta: la extensión de VS Code muestra diffs inline más cómodos para revisar cambios grandes, y la app de escritorio da sesiones paralelas con worktrees automáticos sin manejarlos a mano. La CLI gana en velocidad y en control fino (flags, modo headless, scripting), no en todos los escenarios.

Retomar sesiones viejas

No existe un comando /recap: para retomar una sesión anterior con contexto, el mecanismo real es /resume.

 Intermedio ▸

Cuándo usarlo

Cuando volvés a una tarea que dejaste a medias hace unos días y no querés reexplicar todo el contexto de cero.

Cómo

/resume                    # picker interactivo de sesiones anteriores
claude --continue          # continúa la conversación más reciente
claude --resume <id>       # continúa una sesión puntual por id

En sesiones muy largas (más de 100k tokens aprox.), Claude Code puede ofrecerte un "Resume from summary" que corre un /compact automático antes de retomar.

Ejemplo

Volver un lunes a la sesión del viernes donde estabas migrando un DAG a TaskFlow API, retomarla con /resume, y pedirle "resumime en tres líneas dónde quedamos" para reubicarte antes de seguir.

Detalle que la mayoría se pierde

Si corriste /clear dentro del mismo proceso de Claude Code, el menú de /rewind muestra una entrada extra al tope para volver a la conversación de antes del /clear — una forma rápida de deshacer un /clear accidental sin pasar por /resume.

Corrección respecto a la lista original: el comando /recap no existe en la documentación oficial. Esta ficha documenta el mecanismo real (/resume) en su lugar.

Memoria persistente

Claude Code ya trae memoria automática nativa (carpeta memory/ por proyecto); armar algo propio sólo se justifica en casos puntuales.

 Experto ▸

Cuándo usarlo

La nativa alcanza para la mayoría de los equipos: aprende sola de tus correcciones sesión a sesión. Justifica armar algo propio cuando necesitás memoria compartida entre todo el equipo (no local a tu máquina), estructura de tipos custom, o integración con un sistema externo (un Notion, una base de conocimiento).

Cómo

La memoria automática está prendida por default. Vive en ~/.claude/projects/<proyecto>/memory/, con un MEMORY.md como índice (se cargan sus primeras 200 líneas o 25KB, lo que sea menor) y archivos de tema aparte que se leen bajo demanda:

~/.claude/projects/<proyecto>/memory/
├── MEMORY.md              # índice, se carga siempre
├── convenciones-dbt.md    # se lee sólo cuando hace falta
└── debugging-airflow.md

Se administra con /memory (ver, editar, desactivar) y es local a tu máquina — no se comparte entre compañeros ni entre entornos cloud.

Ejemplo

Después de corregir varias veces que "los tests de dbt en este repo corren con dbt test --target ci, no con el target default", Claude guarda esa nota sola en memoria — la próxima sesión ya lo sabe sin que se lo repitas.

Detalle que la mayoría se pierde

La memoria automática es machine-local: si el equipo comparte laptops o corre Claude Code en un entorno cloud efímero, esas notas no viajan con vos. Para eso sirve compartir vía CLAUDE.md (versionado en git) en vez de depender de la memoria automática. Además, la memoria del subagente principal no se carga dentro de los subagentes (salvo fork) — cada subagente puede tener su propia memoria separada si se configura el campo memory en su frontmatter.

Relacionado: CLAUDE.md · CLAUDE.md vivo

24

Hooks productivos

Scripts que corren automáticamente en eventos del ciclo de vida de la sesión — no dependen de que el modelo se acuerde de hacer algo.

 Experto ▸

Cuándo usarlo

Cuando una regla tiene que cumplirse siempre, sin excepción, más allá de lo que diga CLAUDE.md — bloquear un comando peligroso, correr un linter después de cada edición, avisar por Slack cuando termina una tarea larga.

Cómo

Configuración en settings.json, con un evento, un matcher opcional y el comando a correr:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "scripts/bloquear-prod.sh",
            "timeout": 10
          }
        ]
      }
    ]
  }
}

Eventos clave: SessionStart / SessionEnd (arranque y cierre de sesión), UserPromptSubmit (antes de procesar tu prompt), PreToolUse / PostToolUse (antes y después de cada herramienta, puede bloquear), Stop (cuando termina un turno), WorktreeCreate/WorktreeRemove, entre otros.

Ejemplo

Un hook PreToolUse sobre Bash que rechaza cualquier comando bq query sin --dry_run que apunte al dataset analytics_prod, forzando el chequeo de costo antes de correr sobre producción.

Detalle que la mayoría se pierde

Un hook es la única forma de bloquear algo de verdad, pase lo que pase con el criterio del modelo — CLAUDE.md y las instrucciones en el prompt son contexto que Claude interpreta, no reglas forzadas. Si la regla es "nunca hagas X", esa regla va en un hook, no en un párrafo de CLAUDE.md por más enfático que suene.

Relacionado: CLAUDE.md · preguntas proactivas

25

Dominio de Git/GitHub

Prerrequisito real para todo lo demás en este nivel: worktrees, checkpoints y revertir cambios del agente dependen de que sepas moverte con git.

 Experto ▸

Cuándo usarlo

Antes de correr subagentes o sesiones en paralelo sobre el mismo repo, y antes de confiar en /rewind como única red de seguridad (no lo es).

Cómo

Un worktree es un checkout separado del mismo repo, con su propia rama, para que dos sesiones no se pisen editando los mismos archivos:

claude --worktree migracion-esquema-ventas

Esto crea (por default) .claude/worktrees/migracion-esquema-ventas/ en una rama nueva worktree-migracion-esquema-ventas. Podés tener una sesión migrando el esquema de ventas en un worktree mientras otra arregla un bug en la DAG de marketing en otro, sin que se toquen los mismos archivos.

Ejemplo

Aislar un subagente que hace refactors mecánicos en paralelo agregando isolation: worktree en su frontmatter, para que sus ediciones no choquen con lo que estás haciendo vos en la sesión principal al mismo tiempo.

Detalle que la mayoría se pierde

/rewind no es un sustituto de git: los checkpoints se borran a los 30 días, no rastrean cambios hechos por bash ni por la mayoría de los subagentes, y no sirven una vez que cerrás la sesión sin haber comiteado. La única red de seguridad real para cambios que importan es un commit (o al menos un git stash) antes de dejar que Claude toque algo grande.

Relacionado: subagentes · rebobinar

26

CLI sobre MCPs

Para muchas tareas, un CLI ya instalado (bq, gcloud, dbt) es más eficiente en tokens que levantar un servidor MCP — pero no siempre.

 Experto ▸

Cuándo usarlo

Cuando ya existe un CLI oficial y bien documentado para lo que necesitás (BigQuery, GCS, dbt) y Claude puede aprender a usarlo leyendo --help o tu CLAUDE.md, en vez de sumar un servidor MCP dedicado sólo para eso.

Cómo

Nada especial: dejar que Claude use Bash para correr bq query --use_legacy_sql=false o dbt run directo, documentando en CLAUDE.md los comandos que más se usan.

Ejemplo

Para consultar el esquema de una tabla de BigQuery, bq show --schema --format=prettyjson dataset.tabla por Bash resuelve lo mismo que un MCP server de BigQuery, sin la carga adicional en contexto de tener ese servidor conectado.

Detalle que la mayoría se pierde

No es una regla absoluta: por default, los MCP servers conectados sólo cuestan ~120 tokens en la configuración inicial (schemas completos diferidos, se cargan bajo demanda vía tool search cuando Claude realmente necesita esa herramienta). El costo real aparece cuando herramientas MCP con schemas grandes se cargan por completo — por ejemplo, si desactivás el tool search con ENABLE_TOOL_SEARCH=false. Un MCP vale la pena cuando expone algo que un CLI no puede: acceso autenticado a un servicio sin CLI propio, estado persistente entre llamadas, o una integración (Slack, Notion) sin equivalente de línea de comandos razonable.

Tareas recurrentes

/loop corre un prompt repetidamente mientras la sesión sigue abierta, con intervalo fijo o dejando que Claude se autorregule el ritmo.

 Experto ▸

Cuándo usarlo

Para chequeos periódicos durante una tarea larga que corre en otro lado: si terminó un backfill, si una DAG que triggereaste manualmente ya terminó, si un deploy de dbt Cloud pasó.

Cómo

/loop 5m fijate si terminó el backfill de la tabla de ventas históricas
en BigQuery y avisame el resultado

Si omitís el intervalo, Claude decide solo cada cuánto volver a chequear. Si omitís el prompt, corre un chequeo de mantenimiento autónomo (o lo que tengas en .claude/loop.md, si existe).

Ejemplo

/loop 10m revisando el estado de una carga incremental grande en BigQuery lanzada por un job de Airflow, para que te avise apenas termine en vez de que vos tengas que ir a mirar la consola cada rato.

Detalle que la mayoría se pierde

Cada iteración del loop consume tokens como cualquier turno normal — un intervalo muy corto sobre una tarea que tarda horas quema presupuesto de sobra chequeando "todavía no" una y otra vez. Conviene elegir el intervalo en función de cuánto tarda en cambiar el estado real que estás mirando, no dejarlo en el default sin pensarlo.

Relacionado: bucle autónomo

Revisión profunda

/code-review ultra lanza una flota de agentes revisores en un sandbox remoto para encontrar bugs reales antes de mergear, con cada hallazgo verificado de forma independiente.

 Experto ▸

Cuándo usarlo

Antes de mergear un cambio grande o sensible — una migración de esquema, un refactor de la lógica de un DAG productivo — donde un /code-review local rápido no da la confianza suficiente.

Cómo

/code-review ultra
/code-review ultra develop     # contra una base distinta a la default
/code-review ultra 1234        # revisa el PR #1234

/ultrareview es alias de /code-review ultra cuando está disponible en tu cuenta. Requiere login con cuenta de claude.ai (no alcanza sólo con API key).

Ejemplo

Correr /code-review ultra sobre una rama que reescribe el particionado de la tabla de hechos de ventas antes de abrir el PR, para que verifique de forma independiente cada hallazgo en vez de tirarte sugerencias de estilo sin chequear.

Detalle que la mayoría se pierde

Tiene límites de uso reales: en plan Pro/Max son 3 corridas gratis de por vida (no se renuevan), Team/Enterprise no tiene gratis ninguna; después cuesta entre ~$5 y $25 en usage credits por corrida, según el tamaño del cambio, facturado aparte del plan normal. No está disponible con Amazon Bedrock, Google Cloud, Microsoft Foundry ni en organizaciones con Zero Data Retention. El límite de diff es 500 archivos / 8000 líneas cambiadas por default — para repos más grandes, sugiere pasar a modo PR. Tarda entre 5 y 10 minutos y corre en background, sin bloquear tu sesión.

Corrección respecto a la lista original: es /code-review ultra (dos palabras, subcomando), no /ultra review. /ultrareview existe como alias de una sola palabra cuando la función está habilitada en la cuenta.

Hospedaje en VPS

Correr Claude Code sin supervisión en un servidor remoto, apoyándose en el modo no interactivo (-p) documentado, más herramientas estándar de sysadmin para que quede corriendo 24/7.

 Experto ▸

Cuándo usarlo

Para automatizaciones que no dependen de que tengas la laptop prendida: un chequeo de calidad de datos que corre cada mañana, un agente que monitorea el estado de DAGs y abre un PR cuando detecta un patrón de fallo repetido.

Cómo

El mecanismo documentado es el modo no interactivo:

claude -p "revisá el estado de las DAGs de la última corrida y \
avisame por Slack si alguna falló más de dos veces seguidas" \
  --allowedTools "Bash,Read" \
  --output-format json

Para dejarlo corriendo 24/7 en un VPS, la forma habitual es envolver ese comando en cron (chequeos periódicos) o systemd/tmux (proceso persistente) — esto ya es administración de servidores estándar, no algo específico de Claude Code.

Ejemplo

Un cron que cada hora corre claude -p --bare con ANTHROPIC_API_KEY seteada, revisa las métricas de frescura de las tablas principales en BigQuery, y sólo escribe algo si encuentra una tabla desactualizada.

Detalle que la mayoría se pierde

El modo --bare no lee tu login de claude.ai — necesita ANTHROPIC_API_KEY propia, que se factura distinto a una suscripción Pro/Max. Un agente 24/7 corriendo cada tanto sobre datos reales suma costo real de API sin que nadie lo esté mirando en vivo — vale la pena poner un tope de gasto y alertas, no asumir que "es automático" significa "es gratis". Para necesidades de equipo más serias (múltiples agentes, infraestructura propia, sesiones que arranca claude.ai pero corren en tu red) existen los entornos self-hosted de Team/Enterprise, un escalón arriba de simplemente poner claude -p en un cron.

31

Bucle autónomo

/goal fija una condición de éxito y Claude sigue iterando por su cuenta, turno tras turno, hasta cumplirla.

 Experto ▸

Cuándo usarlo

Para tareas que requieren varias vueltas de prueba-y-error sin que necesites estar confirmando cada paso — hacer pasar un test suite completo, converger un modelo de dbt hasta que compile sin errores en los tres entornos.

Cómo

/goal hacé que `dbt build --select tag:diario` pase sin errores
ni warnings en el target de staging

/goal clear   # cancela el objetivo activo antes de tiempo

/goal sin argumentos muestra el objetivo activo (o el último cumplido). Para cancelarlo antes de tiempo, además de clear también aceptan stop, off, reset, none o cancel.

Ejemplo

Fijar como objetivo que los tests de schema.yml de dbt pasen para todos los modelos de un dominio, y dejar que Claude itere solo corrigiendo tests rotos uno por uno hasta que el suite completo esté verde.

Detalle que la mayoría se pierde

Un objetivo mal definido ("mejorá la calidad de los datos") no tiene condición de parada clara, así que Claude puede iterar de más buscando qué más tocar. Definilo con un criterio verificable de forma automática (un comando que devuelve éxito o falla), no con una aspiración — es la diferencia entre un bucle que converge y uno que da vueltas gastando tokens sin rumbo.

Relacionado: tareas recurrentes

Agent SDK

Librería (Python, TypeScript, o vía CLI) que expone el mismo loop de agente, manejo de contexto y herramientas de Claude Code, para construir tu propia interfaz programática.

 Experto ▸

Cuándo usarlo

Cuando necesitás Claude como pieza de una aplicación propia (un servicio interno de triage de incidentes de datos, un bot de Slack que responde preguntas sobre el warehouse) y no como sesión interactiva de terminal.

Cómo

Paquetes oficiales claude-agent-sdk (Python) y @anthropic-ai/claude-agent-sdk (TypeScript), o la variante más simple, el CLI en modo no interactivo:

claude -p "encontrá y arreglá el bug en el DAG de ventas" \
  --allowedTools "Read,Edit,Bash"

Ejemplo

Un servicio interno en Python que usa el SDK para recibir una alerta de calidad de datos, armar un prompt con el contexto de la tabla afectada, y devolver un diagnóstico estructurado — sin que nadie tenga que abrir una terminal.

Detalle que la mayoría se pierde

Con el Agent SDK, vos hospedás y operás el agente en tu propia infraestructura — Anthropic te da la librería, no el hosting. Eso es distinto de un servicio administrado por Anthropic, donde ellos corren el sandbox. Si sólo necesitás automatizar tareas puntuales sin construir una app nueva alrededor, claude -p a secas (sin meterse con el SDK de Python/TS) suele alcanzar y es más simple de mantener.
