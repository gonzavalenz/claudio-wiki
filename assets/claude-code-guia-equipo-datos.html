Capítulo 01 · docs/01-fundamentos.md

Fundamentos: LLM, agente y agentic loop

En 30 segundos

Un LLM solo predice texto. Claude Code es un agente: el mismo modelo, envuelto en un programa (el harness) que le da tools para leer, editar y ejecutar cosas en tu máquina, y que le devuelve el resultado de cada acción para que decida el paso siguiente. Ese ciclo es el agentic loop. Lo que más limita a un agente no es la inteligencia del modelo, sino el context window.

LLM vs. agente

LLM "a secas" (chat)Agente (Claude Code)
Qué haceRecibe texto, devuelve textoRecibe una tarea y actúa hasta resolverla
Ve tu códigoSolo lo que le peguesLo busca y lo lee solo
Ejecuta cosasNoSí: comandos, tests, git, dbt, bq...
VerificaNo sabe si lo que dijo funcionaCorre el test, lee el error, corrige
Tu rolCopiar y pegar entre pasosDar contexto, dirigir y revisar

El modelo detrás es el mismo. La diferencia la pone el harness: la capa que le da herramientas al modelo y administra qué contexto ve.

El agentic loop

Según la documentación oficial, el loop tiene tres fases que se mezclan entre sí:

  1. Juntar contexto: buscar archivos, leer código, mirar git status, leer errores.
  2. Actuar: editar archivos, correr comandos.
  3. Verificar: correr tests o el comando que corresponda y ver si funcionó.

Se repite hasta que la tarea está resuelta. Cada uso de una tool devuelve información nueva que alimenta la siguiente decisión. Vos también sos parte del loop: podés interrumpir en cualquier momento (Esc) o mandar una corrección mientras trabaja (ver Plan mode y checkpoints).

Las tools: lo que lo hace agente

CategoríaQué puede hacer
ArchivosLeer, editar, crear, renombrar
BúsquedaEncontrar archivos por patrón, buscar contenido con regex
EjecuciónCorrer comandos de shell, tests, git, servidores
WebBuscar en la web, leer documentación, buscar mensajes de error
Code intelligenceVer errores de tipos, ir a definiciones (requiere plugins de code intelligence)

Además tiene tools para lanzar subagents, hacerte preguntas y orquestar trabajo. Todo lo demás (skills, MCP, hooks, plugins) son capas que se suman encima de este loop.

Qué ve Claude cuando arranca

Cuando corrés claude en una carpeta, tiene acceso a:

  • Tu proyecto: la carpeta y subcarpetas (y otras rutas si lo autorizás).
  • Tu terminal: cualquier comando que vos podrías correr.
  • Tu estado de git: rama actual, cambios sin commitear, commits recientes.
  • Tu CLAUDE.md y la auto memory (ver Memoria).
  • Las extensiones que configures: MCP, skills, subagents.

Lo que no ve: la conversación de sesiones anteriores. Cada sesión arranca con un context window nuevo. Lo que tiene que sobrevivir entre sesiones va en CLAUDE.md.

Ejemplo: un test de dbt que falla

Le pedís:

el test not_null de fct_pedidos.cliente_id está fallando en dev. Encontrá por qué y arreglalo.

Lo que hace el loop, vuelta por vuelta:

  1. Corre dbt test --select fct_pedidos para ver el error real.
  2. Lee models/marts/fct_pedidos.sql y el schema.yml.
  3. Sigue el ref() hasta stg_pedidos.sql y ve que hay un LEFT JOIN a clientes.
  4. Corre una query con bq query para contar cuántas filas quedan con cliente_id nulo.
  5. Propone el cambio (filtrar, o cambiar el join), lo edita.
  6. Vuelve a correr dbt test --select fct_pedidos para confirmar.

No le dijiste qué archivos abrir ni qué comandos correr: eso lo resuelve el loop. Vos aportás lo que no está en el código (por ejemplo, "los pedidos sin cliente son pedidos de prueba, se pueden filtrar").

Trucos y errores comunes

Trucos
  • Delegá, no dictes. Dale el objetivo y el contexto que solo vos sabés; dejá que él elija los pasos. "El checkout falla con tarjetas vencidas, el código está en src/payments/" rinde más que una lista de 10 pasos.
  • Dale una forma de verificar. Es lo que más mejora el resultado: un test, un dbt build --select, una query de control, un output esperado. Sin verificación, el agente entrega algo plausible, no algo correcto.
  • Es una conversación. Si el primer intento no es lo que querías, no arranques de cero: corregí ("no, el problema está en el manejo de la sesión").
  • El context window es el recurso escaso. Cada archivo leído y cada output de comando lo ocupa. Sesiones largas y mezcladas rinden peor. Ver Contexto.
  • Claude Code te puede enseñar a usarlo. Preguntale "¿cómo configuro un hook?" o "¿cómo debería armar mi CLAUDE.md?".

Capítulo 02 · docs/02-que-es-claude-code.md

Qué es Claude Code y dónde vive

En 30 segundos

Claude Code es el agente de Anthropic para trabajar con código (y con cualquier cosa que se haga desde una terminal). Es un solo motor disponible en varias superficies: CLI, app de escritorio, VS Code, JetBrains, web y móvil. Cambia la interfaz, no el comportamiento: tu CLAUDE.md, tus settings y tus servidores MCP valen en todas las superficies locales.

Qué es

Un modelo Claude + un harness que le da tools y maneja el contexto (ver Fundamentos). No sirve solo para programar: también para escribir documentación, investigar un repo, correr builds, analizar logs o armar queries.

Dónde se usa

SuperficieIdeal paraQué tiene
CLI (claude)Trabajo en terminal, scripts, servidores remotosEl set completo de features. Es la única con modo no interactivo (claude -p) y Agent SDK
Desktop (Mac, Windows, Linux)Revisión visual, varias sesiones en paraleloVisor de diffs, preview de la app, sesiones paralelas
VS Code / CursorTrabajar sin salir del editorDiffs inline, @-menciones, revisión del plan
JetBrains (PyCharm, IntelliJ...)Trabajar dentro de un IDE JetBrainsCorre el CLI en la terminal del IDE + visor de diffs
Web (claude.ai/code)Tareas largas que no necesitan mucha supervisiónCorre en la nube, sigue aunque cierres la compu
Móvil (app de Claude)Lanzar y monitorear tareas desde el celularSesiones en la nube y Remote Control de sesiones locales

Podés mezclar superficies en el mismo proyecto.

Dónde corre el código

EntornoDónde se ejecutaPara qué
LocalTu máquinaLo normal. Acceso a tus archivos, credenciales y herramientas (gcloud, bq, dbt)
CloudVMs de Anthropic (o entornos self-hosted de tu organización)Delegar tareas, trabajar sobre repos que no tenés clonados
Remote ControlTu máquina, manejada desde el navegador o el celularSeguir una sesión local desde otro dispositivo

Para el stack de datos, lo habitual es local: ahí están tus credenciales de GCP y tu perfil de dbt. Una sesión cloud no tiene acceso a tu gcloud auth local.

Relación con la Claude API y el Agent SDK

  • La Claude API te da el modelo "crudo": le mandás mensajes, te devuelve texto o pedidos de tool use. El loop, las tools y los permisos los programás vos.
  • Claude Code trae todo eso resuelto: tools probadas, agentic loop, permisos, memoria, sesiones.
  • El Agent SDK expone el mismo harness de Claude Code como librería (Python/TypeScript), para armar tus propios agentes sin reimplementar el loop.

Regla rápida: para trabajar vos día a día, Claude Code. Para meter un agente dentro de un producto o pipeline propio, Agent SDK (ver Automatización).

Cómo se extiende

PiezaQué esCuándo se cargaCapítulo

Ejemplo: qué superficie usar para qué

  • Refactor de un DAG de Airflow con tests locales → CLI o VS Code, en local.
  • Revisar con calma un diff grande de modelos dbt → Desktop o VS Code (visor de diffs).
  • "Investigá por qué este repo viejo de ingestas usa dos versiones de pandas" y dejarlo corriendo → Web.
  • Chequear desde el celular si terminó la sesión que dejaste corriendo → Remote Control o app móvil.

Trucos y errores comunes

Trucos
  • La extensión de VS Code trae su propio CLI para el panel de chat. Para correr claude en la terminal integrada igual necesitás instalar el CLI.
  • Las sesiones son por superficie: Desktop, web y VS Code tienen cada una su lista de sesiones (Desktop puede retomar una sesión del CLI).
Cuidado
  • El plugin de JetBrains no trae CLI: corre claude en la terminal del IDE. Si no está en el PATH, muestra "Cannot launch Claude Code".
  • No es un autocompletado: no sugiere la línea siguiente, resuelve tareas completas de varios pasos.

Capítulo 03 · docs/03-instalacion.md

Instalación y primeros pasos

En 30 segundos

Instalá con el instalador nativo (curl -fsSL https://claude.ai/install.sh | bash), abrí una terminal nueva, entrá a tu repo y corré claude. La primera vez te pide login en el navegador. Después corré /init para generar el CLAUDE.md y arrancá con una tarea chica.

Requisitos

  • Sistema: macOS 13+, Windows 10 1809+, Ubuntu 20.04+, Debian 10+ o Alpine 3.19+. 4 GB de RAM.
  • Shell: Bash, Zsh, PowerShell o CMD.
  • Cuenta: Pro, Max, Team, Enterprise o Console (API). El plan gratis de claude.ai no incluye Claude Code. También funciona con proveedores cloud (Amazon Bedrock, Google Cloud's Agent Platform —ex Vertex AI—, Microsoft Foundry).

Primera sesión en un repo

  1. Pararte en la raíz del repo (cd). Claude Code trabaja sobre la carpeta donde lo abrís.
  2. Aceptar el diálogo de confianza (workspace trust) la primera vez: te muestra qué permisos o hooks trae el repo.
  3. Correr /init: analiza el proyecto y genera un CLAUDE.md con comandos de build/test y convenciones. Si ya existe, propone mejoras en vez de pisarlo.
  4. Pulir el CLAUDE.md con lo que Claude no puede deducir del código (ver Memoria).
  5. Arrancar con preguntas, no con cambios:
¿cómo está organizado este proyecto dbt? ¿qué capas hay y cómo se nombran los modelos?
  1. Después, una tarea chica y verificable:
agregá un test unique sobre pedido_id en stg_pedidos y corré dbt test --select stg_pedidos

Atajos que conviene saber desde el día uno: / lista comandos, Shift+Tab cambia el modo de permisos, Esc frena a Claude, /help muestra la ayuda. Ver Comandos.

Formas de lanzar claude

claude                                   # sesión interactiva
claude "explicá qué hace dags/ingesta_ventas.py"   # interactiva con un prompt inicial
claude -p "listá los modelos sin tests"  # una consulta y sale (modo no interactivo)
claude -c                                # continúa la última conversación en esta carpeta
claude -r                                # elige una sesión anterior de una lista
claude -n migracion-staging              # arranca con un nombre de sesión

Actualizar

La instalación nativa se actualiza sola en segundo plano. Para forzarlo:

claude update

Trucos y errores comunes

Trucos
  • Para actualizar con npm, npm install -g @anthropic-ai/claude-code@latest. npm update -g puede no llevarte a la última versión.
  • Abrí claude en la raíz del repo, no en tu home: la carpeta define qué CLAUDE.md se carga, a qué archivos tiene acceso y dónde se guardan las sesiones.
  • Si algo anda raro, /doctor dentro de la sesión diagnostica (y puede arreglar) problemas de instalación y configuración.
  • Lo demás es incremental: skills, hooks, MCP y plugins se suman cuando hacen falta. No los necesitás para empezar.
Cuidado
  • No uses sudo npm install -g: genera problemas de permisos. Preferí el instalador nativo.

Modelos: cuál usar para qué

En 30 segundos

Hay cuatro familias (Fable, Opus, Sonnet, Haiku) y dos perillas: qué modelo (/model) y cuánto razona (/effort). El default suele ser Opus con esfuerzo medium, y alcanza para casi todo. Subí el esfuerzo o pasá a Fable para problemas difíciles y largos; bajá a Sonnet/Haiku o a esfuerzo low para tareas mecánicas.

Familias y cuándo usar cada una

AliasPara quéComentario
fableLas tareas más difíciles y largas: root cause de incidentes, decisiones de arquitectura, trabajo de varias horasEl más capaz. No es el default en ningún plan. En algunos planes se cobra con usage credits
opusRazonamiento complejo y trabajo diario exigenteEl default en Pro, Max, Team, Enterprise y API
sonnetProgramación del día a díaMás barato que Opus
haikuTareas simples y rápidasEl más rápido y barato
opusplanOpus mientras planifica, Sonnet al ejecutarCombina buen plan con ejecución barata
bestFable si lo tenés disponible; si no, Opus
defaultVuelve al modelo por defecto de tu cuentaBorra cualquier override

Los alias apuntan a la versión recomendada y se actualizan solos. Dependen del proveedor: con la API de Anthropic, opus y sonnet son Opus 5.5 y Sonnet 5.5; en Google Cloud's Agent Platform, sonnet todavía apunta a Sonnet 4.5. Para fijar una versión usá el nombre completo (ej. claude-opus-5-5).

Para ver qué modelo estás usando: /status, o mostralo en la status line (ver Contexto).

Esfuerzo (/effort)

El esfuerzo controla cuánto razona el modelo en cada paso. Más esfuerzo = más tokens y más tiempo, pero prueba más casos borde y verifica más.

NivelCuándo
lowCambios chicos que vas revisando uno por uno: renombrar, un primer borrador, brainstorming
mediumDefault en Opus 5.5 y Sonnet 5.5. Trabajo diario con alcance claro
highCuando importa verificar o hay casos borde: arreglar un bug en código existente
xhighRazonamiento más profundo, más gasto
maxProblemas difíciles que querés que resuelva solo. Puede "sobrepensar": probalo antes de adoptarlo
/effort            # abre el slider
/effort high       # lo fija y lo guarda como default para este modelo
/effort auto       # vuelve al default del modelo

También: claude --effort high al lanzar, o las flechas izquierda/derecha dentro de /model. max se aplica solo a la sesión actual.

Para un solo turno, escribí ultrathink en el prompt: pide razonamiento más profundo en ese mensaje sin cambiar el esfuerzo de la sesión. Frases como "think hard" ya no son palabras clave: se mandan como texto normal.

Fast mode

/fast (o Option+O / Alt+O) activa una configuración de Opus hasta 2,5x más rápida, con mayor costo por token. Misma calidad, no es otro modelo. Solo funciona en Opus (5.5, 5 y 4.8); en planes de suscripción se cobra con usage credits. Mientras está activo ves un ↯ junto al prompt. Conviene activarlo al principio de la sesión, no a mitad.

Ejemplo: elegir según la tarea

TareaConfiguración razonable
Agregar description a 40 columnas en schema.ymlsonnet o haiku, esfuerzo low
Implementar un modelo incremental nuevo en dbt con testsDefault (opus, medium)
Bug intermitente en un DAG de Airflow que duplica filas en BigQueryopus con high, o fable
Diseñar la migración de 30 modelos legacy a una arquitectura por capasopusplan o fable, empezando en plan mode
Iterar rápido en vivo sobre una query que estás depurando/fast

Trucos y errores comunes

Trucos
  • Empezá con el default. Cambiá cuando tengas un motivo: resultados flojos → más esfuerzo; tarea mecánica → menos.
  • Un modelo más grande no compensa un mal prompt. Contexto claro y una forma de verificar rinden más que subir de modelo.
  • /model guarda el default. Si querés probar un modelo solo para esta sesión, abrí el selector y apretá s.
  • Los subagents heredan el modelo de la sesión, salvo que su definición fije otro. Si pasás a Opus antes de que delegue búsquedas, esas búsquedas también corren en Opus.
  • Con Fable, describí el resultado, no los pasos. Está pensado para problemas ambiguos y largos; no hace falta recordarle que verifique.
  • Contexto de 1M tokens: Sonnet 5.5, Fable y Opus 4.7+ ya corren con context window de 1M en la API de Anthropic, sin elegir variante [1m]. Que entre más no significa que convenga llenarlo (ver Contexto).
Cuidado
  • Cambiar de modelo a mitad de sesión invalida el prompt cache (Claude Code puede pedirte confirmación). Si vas a cambiar, mejor al principio.

Capítulo 05 · docs/05-contexto.md

Contexto: el recurso que más hay que cuidar

En 30 segundos

El context window es todo lo que Claude "tiene en la cabeza" en una sesión: tu conversación, cada archivo que leyó, cada output de comando, CLAUDE.md, skills y el system prompt. Cuando se llena, rinde peor y cuesta más. Regla de oro: una tarea por sesión, /clear entre tareas, /compact con instrucciones cuando la tarea es larga, y /context para ver qué lo está ocupando.

Qué ocupa el context window

Se carga al arrancarSe va sumando mientras trabaja
System promptCada mensaje tuyo y cada respuesta
CLAUDE.md (usuario, proyecto, local) y rules sin paths:Cada archivo que lee (el contenido completo, aunque en pantalla veas solo "Read")
Auto memory (MEMORY.md, primeras 200 líneas o 25 KB)Cada output de comando (dbt build, bq query, logs...)
Nombres de tools MCP (los schemas se cargan bajo demanda)Rules con paths: y CLAUDE.md de subcarpetas, cuando toca archivos que matchean
Descripciones de una línea de las skillsEl cuerpo de una skill cuando se usa
Info del entorno y snapshot de gitLo que agregan los hooks

Lo que no ocupa tu contexto: el trabajo de un subagent. Corre en su propio context window y solo te devuelve el resumen.

Sesiones: retomar y bifurcar

Cada sesión se guarda localmente (en ~/.claude/projects/) y queda atada a la carpeta.

claude --continue            # (-c) retoma la última conversación de esta carpeta
claude --resume              # (-r) selector de sesiones
claude --resume vista-ventas # retoma una sesión por nombre
claude -n vista-ventas       # arranca una sesión ya con nombre

Dentro de una sesión:

Señales de contexto degradado

  • Repite errores que ya le corregiste o "se olvida" de una instrucción que diste hace rato.
  • Le corregiste lo mismo más de dos veces.
  • Mezcla detalles de una tarea anterior con la actual.
  • Las respuestas se vuelven lentas y genéricas.
  • /context o la status line muestran el contexto muy lleno.

Qué hacer: si la tarea sigue, /compact con instrucciones. Si está contaminada de intentos fallidos, /clear y un prompt nuevo mejor, que incluya lo que aprendiste. Una sesión limpia con buen prompt casi siempre le gana a una larga con correcciones acumuladas.

Monitorear con la status line

La status line es una barra configurable debajo del prompt. La forma más rápida:

/statusline mostrá el modelo y el porcentaje de contexto usado con una barra de progreso

O a mano, en ~/.claude/settings.json:

{
  "statusLine": {
    "type": "command",
    "command": "jq -r '\"[\\(.model.display_name)] \\(.context_window.used_percentage // 0)% context\"'"
  }
}

El script recibe un JSON por stdin con campos como model.display_name y context_window.used_percentage (requiere jq instalado).

Trucos y errores comunes

Trucos
  • Una tarea, una sesión. La "sesión cajón de sastre" (empezás con un modelo, preguntás algo de Airflow, volvés al modelo) es el error más común.
  • Poné nombre antes de /clear (/rename o /clear nombre-de-la-anterior) para encontrarla después en /resume.
  • Investigaciones grandes, a un subagent: "usá subagents para investigar cómo se cargan las tablas raw de ventas". Los archivos que lea no ocupan tu contexto.
  • Acotá lo que pedís leer. "Investigá el repo" sin límites puede leer cientos de archivos. Decí dónde mirar.
  • !comando también ocupa contexto: el comando que corrés con ! y su output entran a la conversación.
  • Dos terminales con la misma sesión mezclan los mensajes en un solo historial. Para probar otra idea, usá /branch o claude --continue --fork-session.
  • Más context window no es mejor contexto. Aunque el modelo tenga 1M tokens, una sesión enfocada rinde más.
Cuidado
  • Cuidado con outputs gigantes: un bq query sin LIMIT o un log completo de Airflow entran enteros al contexto. Pedí head, filtros o resúmenes.

Memoria: que no haya que reexplicar el proyecto cada vez

En 30 segundos

Cada sesión arranca sin recordar las anteriores. Dos mecanismos cargan conocimiento entre sesiones: CLAUDE.md (instrucciones que escribís vos, se cargan siempre) y auto memory (notas que Claude guarda solo a partir de tus correcciones). Un buen CLAUDE.md es corto (menos de 200 líneas), concreto y solo tiene lo que Claude no puede deducir leyendo el código.

  • Los de subcarpetas se cargan bajo demanda, cuando Claude lee archivos de esa subcarpeta.
  • Los comentarios HTML (<!-- nota para humanos -->) se eliminan antes de mandarlos al modelo: sirven para notas de mantenimiento sin gastar tokens.
AGENTS.md

Si el repo tiene AGENTS.md (el formato que usan otros agentes) y no tiene CLAUDE.md, Claude Code lee el AGENTS.md. Si hay los dos, por defecto lee solo CLAUDE.md. - Un modelo staging por tabla fuente, nombre `stg_<fuente>__<tabla>`.

Las rules sin paths: se cargan siempre, como el CLAUDE.md.

Auto memory

Claude guarda notas solo cuando algo le parece útil para el futuro: tu rol y preferencias, correcciones que le hiciste, decisiones del proyecto que no están en el código, dónde encontrar cosas externas (un tablero, un tracker).

  • Está activada por defecto en sesiones locales.
  • Se activa/desactiva desde /memory (guarda autoMemoryEnabled en ~/.claude/settings.json), o con "autoMemoryEnabled": false en los settings de un proyecto.
  • Son archivos Markdown comunes: podés leerlos, editarlos o borrarlos.
  • No se comparte entre máquinas ni con la nube.

Cuando le decís "acordate de que en este repo usamos uv, no pip", va a la auto memory. Si querés que vaya al CLAUDE.md (y que lo vea el equipo), decilo: "agregá esto al CLAUDE.md".

Proyecto dbt sobre BigQuery. Capas: staging → intermediate → marts.

- Instalar deps: `uv sync && dbt deps`
- Build de lo modificado: `dbt build --select state:modified+ --defer --state prod-artifacts/`
- Un modelo y sus tests: `dbt build --select <modelo>`
- Lint SQL: `sqlfluff lint models/`

## Convenciones
- Nombres: `stg_<fuente>__<tabla>`, `int_<entidad>_<verbo>`, `fct_<proceso>`, `dim_<entidad>`.
- Toda PK tiene tests `unique` y `not_null` en el `schema.yml` del modelo.
- Tablas de más de 1 GB: `materialized='incremental'` con `partition_by` por fecha.
- Fuentes solo vía `source()`, nunca nombres de tabla hardcodeados.

## Entorno
- Target dev escribe en el dataset `dbt_<usuario>` del proyecto `analytics-dev`. Nunca correr con `--target prod`.
- Antes de una query exploratoria con `bq`, usar `--dry_run` para ver bytes procesados.

## Git
- Ramas `feat/`, `fix/`. PR contra `main`, nunca push directo.

## Compact Instructions
Al compactar, conservá la lista de modelos modificados y los comandos de test usados.

Trucos y errores comunes

Trucos
  • Cuándo agregar algo: cuando Claude comete el mismo error dos veces, cuando un code review encuentra algo que "tendría que haber sabido", o cuando te encontrás reescribiendo la misma aclaración en cada sesión.
  • Reglas contradictorias entre archivos (usuario vs. proyecto vs. subcarpeta) hacen que elija una al azar. Revisalos cada tanto o corré /doctor prompt-audit.
  • CLAUDE.local.md en un worktree solo existe en ese worktree. Para preferencias personales compartidas entre worktrees, importá un archivo de tu home: @~/.claude/mis-notas-dbt.md.
  • Tener un CLAUDE.local.md hace que deje de leer el AGENTS.md si el repo dependía solo de este. Importá el AGENTS.md desde un CLAUDE.md.
  • Versioná el CLAUDE.md del proyecto y tratalo como código: revisalo en los PRs.
Cuidado
  • Si ignora una regla, probablemente el archivo es muy largo o la regla es vaga. "Usá 2 espacios de indentación" funciona; "formateá bien" no. Si una sola regla se saltea siempre, un IMPORTANTE en esa línea ayuda (si marcás todo, no destaca nada).
  • Procedimientos de varios pasos no van en CLAUDE.md: van en una skill, que se carga solo cuando hace falta. Regla: si aplica siempre, CLAUDE.md; si aplica a veces, skill o rule con paths:.

Permisos: cuánta autonomía le das

En 30 segundos

Dos capas. El modo de permisos (se cambia con Shift+Tab) define la base: qué hace sin preguntar. Las reglas allow / ask / deny en settings.json ajustan herramienta por herramienta. deny gana siempre. Los permisos los hace cumplir Claude Code, no el modelo: escribir "no hagas push" en CLAUDE.md es un pedido; una regla deny es una barrera.

Modos de permisos

ModoQué corre sin preguntarPara qué
default (se muestra como Manual)Solo lecturasRevisar cada acción: código sensible, repo desconocido
acceptEditsLecturas, edición de archivos y comandos de filesystem comunes (mkdir, touch, mv, cp, rm, sed) dentro del proyectoIterar revisando los cambios después con git diff
planLecturas y exploración. No edita tu código hasta que apruebes el planExplorar y planificar antes de tocar nada (ver Plan mode)
autoTodo, pero un modelo clasificador revisa cada acción en segundo plano y bloquea lo riesgosoTareas largas, menos interrupciones
dontAskSolo lo pre-aprobado; todo lo que preguntaría, se rechazaCI y scripts con allowlist exacta
bypassPermissionsTodoSolo en contenedores o VMs aislados

Desde la versión 2.1.283, las sesiones interactivas en terminal y VS Code arrancan en auto si tu cuenta y modelo lo soportan; si no, en Manual.

Cambiar de modo:

  • Shift+Tab cicla: auto → default → acceptEdits → plan → auto. La barra de estado muestra el modo activo (⏸ manual mode on, ⏵⏵ accept edits on, ⏸ plan mode on, ⏵⏵ auto mode on).
  • Al lanzar: claude --permission-mode plan.
  • Fijar tu propio modo por defecto en settings (ejemplo): "permissions": { "defaultMode": "acceptEdits" }.

auto reduce interrupciones pero no garantiza seguridad. Usalo cuando confiás en la dirección general de la tarea, no como reemplazo de revisar operaciones sensibles.

Reglas: allow, ask, deny

Formato: Herramienta o Herramienta(especificador).

{
  "permissions": {
    "allow": [
      "Bash(dbt compile *)",
      "Bash(dbt build --select *)",
      "Bash(dbt test *)",
      "Bash(sqlfluff lint *)",
      "Bash(uv run pytest *)",
      "Bash(bq show *)",
      "Bash(bq ls *)"
    ],
    "ask": [
      "Bash(bq query *)",
      "Bash(git push *)"
    ],
    "deny": [
      "Bash(bq rm *)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}

Orden de evaluación: deny → ask → allow. Gana la primera que matchea, sin importar cuál es más específica. Por eso ask: Bash(bq query *) pregunta también en bq query --dry_run ... aunque haya un allow más específico.

Sandbox

El sandbox es un límite que impone el sistema operativo sobre los comandos de shell que corre Claude: qué carpetas puede escribir y a qué dominios de red puede salir. Funciona en macOS, Linux y WSL2 (no en Windows nativo). Está apagado por defecto.

/sandbox

O en settings: "sandbox": { "enabled": true }. En el modo auto-allow, los comandos que corren dentro del sandbox no piden aprobación; los deny y los ask con comando específico (como Bash(git push *)) se siguen respetando.

Permisos y sandbox se complementan: los permisos deciden qué tools puede usar; el sandbox limita lo que un comando puede alcanzar aunque se haya colado algo (por ejemplo, un prompt injection en un archivo que leyó).

Trucos y errores comunes

Trucos
  • Poné el * después del subcomando. Bash(git log *) limita a git log; Bash(git *) habilita cualquier git, incluido push.
  • Una barra no es ruta absoluta: Read(/secrets/**) en settings de usuario apunta a ~/.claude/secrets/**. Para absoluta, //.
  • /fewer-permission-prompts escanea tus sesiones y propone una allowlist de comandos de solo lectura para .claude/settings.json. Muy útil después de la primera semana.
  • Ampliá la autonomía de a poco: empezá restrictivo en un repo nuevo y abrí a medida que conocés cómo trabaja.
Cuidado
  • Las reglas de Bash no son una barrera infalible. deny: Bash(git push *) no matchea git -C . push. Para restricciones que tienen que cumplirse sí o sí, combiná con sandbox o un hook PreToolUse.
  • Un archivo .claudeignore no tiene efecto: para que no lea secretos, usá deny con Read(...).
  • Los checkpoints no deshacen efectos remotos: un bq rm, un DELETE en BigQuery o un deploy no se revierten con /rewind. Eso se controla con permisos, no con checkpoints.
  • Confirmá siempre lo destructivo o visible para otros: git push --force, reset --hard, borrar tablas, crear PRs, mandar mensajes. El costo de confirmar es bajo; el de un error, alto.

Plan mode, interrupciones y checkpoints

En 30 segundos

Separá pensar de hacer. En plan mode (Shift+Tab o /plan) Claude explora y propone un plan sin tocar tu código; vos lo aprobás o lo corregís. Mientras trabaja, Esc lo frena sin perder lo hecho. Y si algo sale mal, Esc Esc o /rewind vuelven código y/o conversación a un punto anterior. Ojo: los checkpoints solo cubren ediciones de archivos de Claude, no comandos de Bash ni efectos remotos.

Plan mode

En plan mode Claude lee archivos, corre comandos para explorar y escribe un plan, pero no edita tu código hasta que lo apruebes.

Cómo entrar:

Cuando el plan está listo, te pregunta cómo seguir:

  • Sí, y usar auto mode (o auto-accept edits si auto no está disponible): aprueba y empieza a editar.
  • Sí, aprobar ediciones a mano: aprueba y te pide confirmación de cada edición.
  • No, seguir planificando: te quedás en plan mode y le decís qué cambiar.

Con Ctrl+G abrís el plan en tu editor y lo modificás directamente antes de aprobar. Para salir sin aprobar, Shift+Tab de nuevo.

Con el modelo opusplan, el plan lo hace Opus y la ejecución Sonnet (ver Modelos).

4. Commitear:

commiteá con un mensaje descriptivo y abrí un PR

quiero armar un pipeline de data quality para las tablas raw de ventas. Entrevistame en detalle usando la tool AskUserQuestion: implementación, casos borde, alertas, tradeoffs. No hagas preguntas obvias. Cuando terminemos, escribí la spec completa en SPEC.md.

Skills: procedimientos que Claude carga solo cuando hacen falta

En 30 segundos

Una skill es una carpeta con un SKILL.md (frontmatter + instrucciones) que le enseña a Claude a hacer una tarea concreta. Claude ve siempre el nombre y la description de cada skill, pero el cuerpo se carga recién cuando la usás (vos con /nombre o Claude solo si la description matchea). Es la forma más barata de tener procedimientos largos sin inflar CLAUDE.md.

Qué es y cómo funciona

Una skill es un procedimiento empaquetado: "cómo revisamos un modelo dbt", "cómo hacemos un backfill en Airflow", "cómo generamos el reporte de costos de BigQuery". Se crea una vez y después se invoca con /nombre, o Claude la usa solo cuando lo que pedís coincide con su description.

Skills y slash commands son lo mismo. Un archivo en .claude/commands/deploy.md y una skill en .claude/skills/deploy/SKILL.md crean el mismo /deploy. Los commands/ viejos siguen andando, pero para cosas nuevas conviene la skill: admite archivos de soporte y más campos de frontmatter.

Progressive disclosure: por qué una skill casi no cuesta contexto

La skill se carga en tres niveles:

NivelQué se cargaCuándo
1. Listadoname + description (+ when_to_use)Siempre, en cada turno, para que Claude sepa que existe
2. CuerpoTodo el SKILL.mdCuando vos o Claude la invocan
3. Archivos de soportereference.md, scripts/, ejemplosSolo si el SKILL.md le indica a Claude que los lea o ejecute

Consecuencia práctica: podés tener una referencia de 400 líneas sobre convenciones de BigQuery en un reference.md y no paga nada hasta que se usa. Lo que sí pagás siempre es la description, así que mantenela corta y precisa.

Skill vs CLAUDE.md vs subagent vs hook
Necesitás…Usá
Un dato que Claude tiene que saber siempre en el repo (comandos de build, convenciones)CLAUDE.md
Un procedimiento que se usa a veces ("cómo hacer X")Skill
Que una tarea ruidosa corra aislada y vuelva solo el resumenSubagent (o skill con context: fork)
Que algo pase sí o sí, sin depender de que el modelo se acuerdeHook

Regla práctica: si una sección de CLAUDE.md empezó a parecer un paso a paso, movela a una skill.

Evaluar e iterar una skill

Que una skill se dispare no significa que funcione. El método oficial es comparar contra una línea base:

  1. Juntá 3–5 pedidos realistas (y 2–3 que no deberían dispararla).
  2. Corré cada uno en una sesión nueva con la skill y otra vez con la skill apagada ("skillOverrides": {"revisar-modelo-dbt": "off"} en settings).
  3. Compará: ¿se disparó cuando debía? ¿el resultado es mejor que sin skill?

Para automatizarlo existe el plugin skill-creator:

/plugin install skill-creator@claude-plugins-official

Después pedile evaluate my revisar-modelo-dbt skill with skill-creator. Arma casos en evals/evals.json, corre cada caso en un subagent limpio, compara con y sin skill, hace A/B entre versiones y propone mejoras a la description midiendo cuándo se dispara y cuándo no. También sirve para crear skills nuevas desde cero.

Trucos y errores comunes

Trucos
  • La description es el 80% del trabajo. Escribila con las palabras que usarías al pedirlo ("revisá el modelo", "validá el dbt") y con el caso de uso principal primero. Si no se dispara, el problema casi siempre está ahí.
  • Si se dispara de más: hacé la description más específica o poné disable-model-invocation: true.
  • El --- tiene que ser la primera línea del archivo, o todo se toma como contenido.
  • El cuerpo queda en el contexto el resto de la sesión y no se relee. Escribí instrucciones que valgan para toda la tarea ("corré los tests después de cada edición"), no pasos de una sola vez. Después de un /compact solo se conservan los primeros ~5.000 tokens de cada skill: lo crítico, arriba.
  • allowed-tools dura un turno y no restringe nada: pre-aprueba esas tools, que corren sin pedirte permiso. Revisá el allowed-tools de skills de repos ajenos antes de correr Claude ahí, porque se aplica incluso en carpetas no confiadas.
  • Si una regla tiene que cumplirse siempre, no la dejes en la skill: pasala a un hook.
  • Demasiadas skills se comen el presupuesto del listado (1% del context window). /skill-doctor te muestra cuánto cuesta cada una y cuáles nunca usaste; poné las de baja prioridad en "name-only" vía skillOverrides.
  • Las skills se recargan solas al editarlas en ~/.claude/skills/ o .claude/skills/; si creaste la carpeta skills/ después de arrancar la sesión, corré /reload-skills.
  • Skills incluidas: Claude Code trae skills listas como /code-review, /simplify, /batch, /loop, /debug y /run//verify. Si creás una skill con el mismo nombre, reemplaza a la incluida.

  • Un comando !` que falla aborta toda la skill. Si esperás exit code 1 (un check que encuentra problemas), agregale || true.

Subagents: delegar sin ensuciar la conversación principal

En 30 segundos

Un subagent es otra instancia de Claude con su propio context window, su propio system prompt y sus propias tools. Hace el trabajo ruidoso (buscar, leer logs, correr tests) aparte y te devuelve solo el resumen. Claude Code trae algunos listos (Explore, Plan, general-purpose) y vos podés definir los tuyos como archivos Markdown en .claude/agents/.

Qué es y cómo funciona

Cuando Claude delega, arranca un subagent con:

  • Su system prompt (el cuerpo del archivo del agente, no el de Claude Code).
  • El mensaje de delegación que escribe Claude.
  • CLAUDE.md y el git status (salvo Explore y Plan, que los saltean para ser rápidos).
  • Las skills precargadas en su campo skills, si tiene.

Lo que no ve: tu conversación, los archivos que ya se leyeron, las skills que ya invocaste. Todo lo que necesite saber tiene que ir en el prompt de delegación. La excepción es un fork (ver más abajo), que hereda la conversación completa.

Cuando termina, a tu conversación vuelve solo el resultado final. Las 40 lecturas de archivos y los 3 intentos fallidos quedan en el contexto del subagent.

2. Revisá cada join: ¿puede ser 1:N y duplicar filas respecto del grano?

4. Buscá `select *`, tablas hardcodeadas en vez de `ref()`/`source()` y filtros que no usan la columna de partición.
5. En modelos `incremental`, revisá `is_incremental()`, `unique_key`, `partition_by` y `cluster_by`.
6. Corré `dbt compile --select <modelo>` y estimá costo con `bq query --dry_run --use_legacy_sql=false` sobre el SQL compilado.

Antes de empezar, consultá tu memoria por problemas recurrentes de este repo. Al terminar, guardá en memoria los patrones nuevos que encontraste.

Formato de respuesta:
- BLOQUEANTE / SUGERENCIA, con `archivo:línea`, qué está mal y qué pasaría en producción.
- Bytes estimados por modelo.
- Si no encontraste nada, decilo explícitamente.

Uso:

@agent-revisor-dbt revisá fct_ventas y dim_clientes, que toqué hoy

Con memory: project, el subagent guarda lo que aprende en .claude/agent-memory/revisor-dbt/ (versionable), así cada revisión arranca sabiendo los errores típicos del repo.

Cómo escribir el prompt de delegación

El subagent arranca en blanco. Un "arreglá el bug" produce resultados genéricos. Un buen prompt incluye:

Objetivo: encontrar por qué el DAG ingesta_ventas duplica filas en raw.ventas desde el 12/09.
Contexto: el DAG está en dags/ingesta_ventas.py; el cambio sospechoso es el PR #231 (cambió el write_disposition).
Ya descartado: no es el source, el archivo de GCS tiene filas únicas.
Alcance: solo lectura, no toques archivos ni corras nada contra prod.
Devolvé: causa probable, archivo:línea y un fix propuesto en menos de 15 líneas.

Qué buscar, qué ya sabés, qué se descartó, límites y formato de la respuesta. Si una regla de CLAUDE.md es crítica para la tarea, repetila en el prompt.

Paralelo, background y forks

  • Paralelo: varias tareas independientes a la vez ("investigá A, B y C en paralelo"). Cada una vuelve con su resumen y Claude los sintetiza.
  • Background: en sesiones interactivas los subagents corren en background por defecto: seguís trabajando y el resultado llega como notificación. Ctrl+B manda a background una tarea que está corriendo. /tasks lista lo que está corriendo (y lo que terminó hace poco).
  • Fork (/subtask <tarea>): un subagent que hereda toda la conversación. Útil cuando explicarle el contexto a un subagent nuevo sería demasiado largo. Comparte el prompt cache con tu sesión, así que es más barato que uno nuevo.
  • Retomar: un subagent custom o general-purpose que terminó se puede continuar ("seguí esa revisión y ahora mirá los tests"). Explore y Plan no se pueden retomar.
  • Límites por defecto: hasta 3 niveles de subagents anidados y 20 corriendo a la vez.

Para varias sesiones en paralelo (no subagents dentro de una), ver Paralelismo y worktrees.

Cuándo sí y cuándo no

Delegá a un subagent cuando…Resolvé en la conversación principal cuando…
La tarea genera mucho output que no vas a volver a mirar (logs, tests, búsquedas)Necesitás ida y vuelta frecuente
Querés limitar tools (un revisor de solo lectura)Las fases comparten mucho contexto (planear → implementar → testear)

Querés una revisión "a ciegas", sin el sesgo de tu conversaciónLa latencia importa: un subagent nuevo tarda en juntar contexto

Para una pregunta sobre algo que ya está en la conversación, usá /btw: ve todo tu contexto, no usa tools y no queda en el historial.

Trucos y errores comunes

Trucos
  • Los subagents en background tienen menos tools (por ejemplo, no pueden preguntarte con AskUserQuestion). Si un subagent depende de algo fuera de ese set, va a fallar distinto en foreground y background.
  • disallowedTools: Bash(git push *) saca Bash entero. Para bloquear solo un comando, usá una regla deny en permisos, que aplica también a subagents.
  • Subagent barato para explorar: definí tu propio Explore en .claude/agents/ con model: haiku y reemplaza al incluido.
Cuidado
  • No delegues entendimiento. Si vos no sabés qué querés, el subagent tampoco. Delegá tareas, no decisiones.
  • Cada subagent gasta tokens propios. Cinco subagents en paralelo son cinco veces el consumo, y si cada uno devuelve un informe largo, igual te llena el contexto. Pedí resúmenes cortos.
  • Las descripciones cuestan contexto siempre. Si la suma de las description de tus subagents pasa los 15.000 tokens, Claude Code avisa al arrancar. Detalle al cuerpo, no a la descripción.
  • Archivos que se ignoran en silencio: sin name, con name pero sin description, YAML roto, o --- que no está en la primera línea. Corré claude plugin validate .claude/agents o claude --debug.
  • Las ediciones de un subagent en background no entran en los checkpoints: /rewind no las deshace, usá git.

Hooks: reglas que no dependen de que el modelo se acuerde

En 30 segundos

Un hook es un comando que Claude Code ejecuta automáticamente en un evento del ciclo de vida (antes de usar una tool, después de editar, al terminar de responder, al arrancar la sesión). Lo corre el harness, no el modelo: pasa siempre. Se configura en settings.json y con exit 2 puede bloquear una acción.

Qué es y cómo funciona

CLAUDE.md es una instrucción que el modelo intenta seguir. Un hook es código que se ejecuta siempre en su evento, sin pasar por el criterio del modelo. Si algo tiene que cumplirse el 100% de las veces ("nunca correr bq rm", "todo .py editado pasa por ruff"), va en un hook.

Flujo: ocurre un evento → si el matcher coincide, Claude Code le pasa al hook un JSON por stdin con el detalle (tool, input, cwd, sesión) → el hook hace lo suyo y responde con su exit code y, opcionalmente, JSON por stdout.

Eventos más útiles

Hay más de 30 eventos; estos cubren el 95% de los casos:

EventoCuándo dispara¿Puede bloquear?Uso típico
PreToolUseAntes de ejecutar una toolSíBloquear comandos peligrosos, validar inputs
PostToolUseDespués de que una tool terminó bienNo (ya se ejecutó), pero le puede avisar a ClaudeFormatear/lintear lo que se editó
UserPromptSubmitAl enviar un prompt, antes de que Claude lo proceseSíAgregar contexto, filtrar prompts
StopCuando Claude termina de responderSí (lo obliga a seguir)Notificar, exigir que pasen los tests
SessionStartAl iniciar, retomar, /clear o después de compactarNoInyectar contexto dinámico
NotificationCuando Claude Code necesita tu atenciónNoNotificación de escritorio
SubagentStart / SubagentStopAl lanzar / terminar un subagentSolo SubagentStopLogs, validar el resultado de un subagent
PreCompact / PostCompactAntes / después de compactarSolo PreCompactGuardar estado antes de perder detalle
PermissionRequestCuando se va a pedir permisoPor JSONAuto-aprobar o negar ciertos pedidos
SessionEndAl cerrar la sesiónNoLimpieza, logs

Otros que existen: PostToolUseFailure, PostToolBatch, StopFailure, ConfigChange, CwdChanged, FileChanged, InstructionsLoaded, WorktreeCreate/WorktreeRemove, TaskCreated/TaskCompleted, Elicitation, entre otros. Lista completa en la referencia oficial.

Cómo se usa

Dónde se configuran
ArchivoAlcance
~/.claude/settings.jsonTodos tus proyectos
.claude/settings.jsonEl repo, compartido con el equipo (se commitea)

Los hooks de distintos archivos se suman, no se pisan. /hooks abre un visor de solo lectura con todos los hooks activos y de dónde viene cada uno. Para editarlos, cambiás el JSON (o se lo pedís a Claude).

Estructura

Tres niveles: evento → grupo con matcher → lista de handlers.

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/ruff.sh" }
        ]
      }
    ]
  }
}
  • matcher: para eventos de tools filtra por nombre de tool. "Bash" exacto, "Edit|Write" lista, y si tiene otros caracteres se toma como regex ("mcp__bigquery__.*"). Vacío u omitido = todos. Distingue mayúsculas.
  • if (opcional, por handler): filtro con sintaxis de permisos sobre tool + argumentos, ej. "Bash(git *)" o "Edit(*.py)". Es best-effort: no lo uses como única barrera de seguridad.
  • type: command (lo más común), http, mcp_tool, prompt (un modelo evalúa y decide) o agent (experimental).
  • timeout: en segundos. Default 600 para command.
  • Usá $CLAUDE_PROJECT_DIR para referenciar scripts del repo sin depender del directorio actual.
Exit codes: cómo responde un hook
Exit codeQué pasa
0OK. En SessionStart y UserPromptSubmit lo que imprimas por stdout se agrega como contexto para Claude
2Error bloqueante. En PreToolUse bloquea la tool; en Stop obliga a seguir; en PostToolUse le muestra el stderr a Claude. El mensaje es tu stderr
Cualquier otro (incluido 1)Error no bloqueante: la acción sigue y ves un aviso

Para control fino, salí con 0 e imprimí JSON. Por ejemplo, en PreToolUse:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Escrituras en prod no permitidas"
  }
}

permissionDecision acepta allow, deny, ask o defer. Un deny de un hook bloquea incluso en bypassPermissions; un allow no salta las reglas deny de tus settings.

Recetas copiables

Todas usan jq para leer el JSON (brew install jq). Acordate de chmod +x en los scripts.

1. Formatear y lintear con ruff después de editar un .py

.claude/hooks/ruff.sh:

#!/bin/bash
f=$(jq -r '.tool_input.file_path // empty')
[[ "$f" == *.py ]] || exit 0

ruff format --quiet "$f"
if ! out=$(ruff check --fix "$f" 2>&1); then
  echo "ruff encontró problemas que no pudo arreglar solo en $f:" >&2
  echo "$out" >&2
  exit 2   # PostToolUse: no deshace la edición, pero Claude ve esto y lo corrige
fi
exit 0

.claude/settings.json:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/ruff.sh" }
        ]
      }
    ]
  }
}

El truco del exit 2 en PostToolUse: Claude recibe el error del linter como feedback y lo arregla en el mismo turno, sin que vos digas nada.

2. Bloquear bq rm, DROP y borrados en GCS

Primera barrera, en permisos (.claude/settings.json):

{
  "permissions": {
    "deny": ["Bash(bq rm *)", "Bash(gsutil rm *)", "Bash(gcloud storage rm *)"]
  }
}

Las reglas de permisos matchean por prefijo de comando; no ven un DROP TABLE escondido dentro de un bq query "...". Para eso, un hook que mira el texto completo. .claude/hooks/bloquear-destructivos.py:

#!/usr/bin/env python3
import json
import re
import sys

data = json.load(sys.stdin)
cmd = data.get("tool_input", {}).get("command", "")

PATRONES = [
    r"\bbq\s+rm\b",
    r"\bDROP\s+(TABLE|SCHEMA|VIEW)\b",
    r"\bTRUNCATE\s+TABLE\b",
    r"\bDELETE\s+FROM\b(?![\s\S]*\bWHERE\b)",  # DELETE sin WHERE
    r"\b(gsutil|gcloud\s+storage)\s+(-m\s+)?rm\b",
]

for patron in PATRONES:
    if re.search(patron, cmd, re.IGNORECASE):
        print(
            f"Bloqueado por hook: el comando matchea '{patron}'. "
            "Si de verdad hace falta, pedile al usuario que lo corra a mano.",
            file=sys.stderr,
        )
        sys.exit(2)

sys.exit(0)
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/bloquear-destructivos.py" }
        ]
      }
    ]
  }
}

Si usás el MCP de BigQuery, sumá un deny sobre su tool de escritura (por ejemplo mcp__bigquery__execute_sql) en permissions.deny.

3. Notificación de macOS cuando Claude termina o necesita algo

En ~/.claude/settings.json (es preferencia personal, no del repo):

{

Si no aparece nada: osascript notifica a través de Script Editor. Corré una vez osascript -e 'display notification "test"' y habilitá Script Editor en Ajustes del Sistema → Notificaciones.

4. Inyectar contexto al iniciar (rama + proyecto GCP activo)

Evita el clásico "corrió contra el proyecto equivocado". En .claude/settings.json:

{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume|compact",
        "hooks": [
          {
            "type": "command",
            "command": "echo \"Rama git actual: $(git branch --show-current). Proyecto GCP activo: $(gcloud config get-value project 2>/dev/null).\""
          }
        ]
      }
    ]
  }
}

En SessionStart, lo que el hook imprime por stdout entra al contexto de Claude. Con compact en el matcher, se vuelve a inyectar después de cada compactación. Escribilo como hechos ("El proyecto activo es X"), no como órdenes: el texto con tono de "instrucción de sistema" puede activar las defensas contra prompt injection.

Trucos y errores comunes

Trucos
  • Probalo a mano antes: echo '{"tool_name":"Bash","tool_input":{"command":"bq rm -t ds.tabla"}}' | .claude/hooks/bloquear-destructivos.py; echo $?.
  • Si imprimís JSON, que sea lo único en stdout. Un echo en tu ~/.zshrc que se ejecuta en shells no interactivos rompe el parseo sin avisar. Envolvelo en if [[ $- == *i* ]].
  • Stop dispara cada vez que Claude termina de responder, no solo al "terminar la tarea". No dispara si lo interrumpiste.
  • Los hooks de tools corren también dentro de subagents, así que tu bloqueo de bq rm los cubre.
  • Hooks de repos ajenos: con claude -p los hooks de .claude/settings.json corren aunque nunca hayas confiado en la carpeta. Revisalos antes de automatizar sobre un repo que no es tuyo.
  • Debug: claude --debug-file /tmp/claude.log y tail -f en otra terminal; Ctrl+O muestra el transcript con los resultados de cada hook.
  • /goal <condición> es un atajo incluido que arma un hook de tipo Stop para que Claude siga trabajando hasta cumplir una condición, sin escribir JSON.
Cuidado
  • exit 1 no bloquea. Es la convención de Unix para error, pero acá es "no bloqueante". Si tu hook es una política, usá exit 2.
  • Un path mal escrito desactiva el hook en silencio: el shell sale con 127, es error no bloqueante y la acción sigue. Mirá el primer aviso después de configurar un hook nuevo.
  • Stop que bloquea en loop: si tu hook obliga a seguir, chequeá stop_hook_active en el input y salí con 0 cuando sea true. Claude Code corta igual después de 8 bloqueos seguidos.
  • PreToolUse no ve los archivos que agregás con @ en el prompt: esos no pasan por una tool. Para bloquear lecturas usá reglas deny de Read.
  • Un hook que da timeout no bloquea: no confíes en un script lento como barrera.

MCP: conectar herramientas y datos externos

En 30 segundos

MCP (Model Context Protocol) es el estándar abierto para enchufarle a Claude Code herramientas externas: GitHub, un navegador, BigQuery, Linear, docs actualizadas. Se agrega un server con claude mcp add, se revisa con /mcp, y sus tools quedan disponibles como cualquier otra, sujetas a los mismos permisos. Antes de sumar uno, preguntate si una CLI que ya tenés (gh, bq, gcloud) no alcanza.

Qué es y cómo funciona

Un server MCP expone tools (y a veces recursos y prompts) que Claude puede usar. Hay dos formas de correrlo:

TransporteQué esEjemplo
http (remoto)Un servicio en la nube; suele autenticar con OAuthLinear, Sentry, Notion, BigQuery de Google
stdio (local)Un proceso que Claude Code levanta en tu máquinaPlaywright vía npx

sse también existe pero está deprecado; usá http.

Las tools de un server se llaman mcp__<server>__<tool> (ej. mcp__github__list_issues). Ese nombre es el que usás en permisos y en matchers de hooks.

Cuánto contexto cuesta un server

Por defecto Claude Code usa tool search: al arrancar solo carga los nombres de las tools y las instrucciones de cada server; la definición completa de una tool se trae cuando Claude la necesita. Por eso sumar servers ya no explota el context window como antes. Igual tiene costo:

  • Las instrucciones de cada server y los nombres de tools se pagan en cada turno.
  • Cada resultado de tool entra al contexto. Claude Code avisa si un resultado pasa los 10.000 tokens y, por encima de 25.000 (default, configurable con MAX_MCP_OUTPUT_TOKENS), lo guarda en un archivo.
  • ENABLE_TOOL_SEARCH=false carga todo de entrada (no lo hagas salvo que tengas un motivo); "alwaysLoad": true en un server hace que sus tools estén siempre visibles.

Mirá el impacto real con /context.

Cómo se usa

Agregar un server
# Remoto (HTTP)
claude mcp add --transport http linear https://mcp.linear.app/mcp

# Remoto con token en header
claude mcp add --transport http github https://api.githubcopilot.com/mcp/ \
  --header "Authorization: Bearer $GITHUB_PAT"

# Local (stdio): todo lo que va después de -- es el comando del server
claude mcp add playwright -- npx -y @playwright/mcp@latest

# Con variables de entorno para el server
claude mcp add --transport stdio --env API_KEY=xxx mi-server -- python server.py

# Desde un bloque JSON que te dio la doc del server
claude mcp add-json clima '{"type":"http","url":"https://api.ejemplo.com/mcp"}'

Gestión:

claude mcp list            # todos los servers configurados
claude mcp get linear      # detalle de uno
claude mcp remove linear   # sacarlo (borra también los tokens OAuth guardados)

Dentro de la sesión, /mcp muestra el estado de cada server (connected, failed, necesita auth), permite autenticar, re-autenticar y deshabilitar un server sin borrarlo.

Scopes: dónde queda guardado
ScopeFlagDónde se guardaPara qué

.mcp.json compartido, sin secretos, usando variables de entorno:

{
  "mcpServers": {
    "linear": { "type": "http", "url": "https://mcp.linear.app/mcp" },
    "interno": {
      "type": "http",
      "url": "${API_BASE_URL:-https://mcp.interno.empresa.com}/mcp",
      "headers": { "Authorization": "Bearer ${MCP_INTERNO_TOKEN}" }
    }
  }
}

La expansión ${VAR} y ${VAR:-default} funciona en command, args, env, url y headers. La primera vez que alguien abre el repo, Claude Code pide aprobar los servers de .mcp.json (se resetea con claude mcp reset-project-choices).

Autenticación OAuth

Para servers remotos con OAuth: agregás el server, abrís /mcp, lo seleccionás y seguís el login en el navegador. Los tokens se guardan de forma segura y se refrescan solos. Desde la terminal también existe claude mcp login <nombre>. En modo headless (claude -p) no hay forma de completar OAuth: autenticá antes en una sesión interactiva.

CLI vs MCP: cuándo conviene cada uno

Claude ya sabe usar CLIs muy bien. Para el stack de datos, muchas veces la CLI gana:

HerramientaCLI¿MCP?
GitHubgh (PRs, issues, Actions, API)Solo si querés que funcione sin gh instalado o en entornos sin shell
BigQuerybq query, bq show, bq ls, --dry_runOpcional (ver abajo). La CLI + reglas de permisos suele alcanzar
GCP en generalgcloud (logging, composer, storage)Rara vez hace falta
NavegadorNo hay CLI equivalenteSí: Playwright

Ventajas de la CLI: cero contexto extra, ya está autenticada con tus credenciales, y la controlás con reglas de permisos del tipo Bash(bq query *). Ventajas del MCP: tools tipadas, OAuth, resultados estructurados y funciona donde no hay shell (Claude Desktop, rutinas en la nube).

Regla práctica: si la CLI existe y está en tu PATH, empezá por la CLI. Sumá un MCP cuando no hay CLI o cuando la integración es claramente mejor.

Mirá el schema de analytics.fct_ventas y decime qué columnas tienen más de 5% de nulls en los últimos 7 días de partición.

Trucos y errores comunes

Trucos
  • El -- es obligatorio en stdio para separar las opciones de Claude de los flags del server. Y --env no puede ir pegado al nombre del server: poné otra opción en el medio.
  • Server que no conecta: /mcp muestra el error; para stdio corré el comando del server a mano en la terminal. Si tarda en arrancar (primer npx), subí MCP_TIMEOUT (ms).
  • En CI, los servers de .mcp.json se cargan sin preguntar con claude -p. Si no los querés, usá --strict-mcp-config con --mcp-config explícito, o --bare.
  • Servers MCP por subagent: el campo mcpServers de un subagent le da un server solo a ese agente, sin cargarlo en tu sesión principal.
Cuidado
  • Seguridad primero. Un server MCP corre con tus credenciales. Usá solo servers de fuentes confiables, preferí usuarios/roles de solo lectura (en DBs, un usuario readonly en el connection string) y negá las tools de escritura con permissions.deny.
  • Prompt injection: un server que trae contenido externo (páginas web, issues, emails) puede meter instrucciones maliciosas en el contexto. No combines ese tipo de server con permisos amplios de escritura.
  • Nada de tokens en .mcp.json. Usá ${VAR} y que cada uno tenga la variable en su entorno, o agregá el server con scope local.
  • url sin type es error: en JSON, una entrada con url necesita "type": "http".
  • Rutas que Claude Code NO lee: ~/.claude/.mcp.json, ~/.claude/mcp.json. Las válidas son ~/.claude.json y .mcp.json en la raíz del repo.
  • claude mcp add no valida credenciales: un token mal puesto se ve recién como failed en /mcp.

  • Un plugin corre código con tus permisos (hooks, servers MCP). Leé el detalle antes de instalar, sobre todo de marketplaces third-party.
  • Solo plugin.json va dentro de .claude-plugin/. Skills, agentes y hooks van en la raíz del plugin; si los ponés adentro de .claude-plugin/, no cargan.
  • El name de la entrada en marketplace.json tiene que coincidir con el name de plugin.json, y las rutas source son relativas a la raíz del marketplace. Son las dos causas más comunes de instalaciones que fallan.
  • Actualizaciones: el marketplace oficial se actualiza solo; los third-party vienen con auto-update apagado (se prende desde la pestaña Marketplaces). La sesión abierta sigue con la versión vieja hasta /reload-plugins.
  • Plugins en la nube: las sesiones cloud y las rutinas no cargan los plugins de tu máquina ni los que habilita el .claude/settings.json del repo. Lo que necesites ahí, commitealo como skill en .claude/skills/.
  • Atajo para algo personal: claude plugin init mi-tool crea un plugin en ~/.claude/skills/mi-tool/ que se carga en todas tus sesiones sin marketplace.
Cuidado
  • Un plugin habilitado cuesta contexto en cada turno, aunque no lo uses: nombres y descripciones de sus skills y agentes van siempre. Deshabilitá lo que no usás; la pestaña Installed de /plugin agrupa los "no usados recientemente" y /skill-doctor muestra el costo.
  • Algunos campos de subagents no aplican en plugins: hooks, mcpServers y permissionMode del frontmatter se ignoran por seguridad. Poné los hooks en hooks/hooks.json y los servers en .mcp.json del plugin.
  • /plugin no funciona en claude -p: instalá desde la shell con claude plugin install; los plugins ya instalados sí cargan en modo headless.

Paralelismo y worktrees: varias tareas a la vez sin pisarse

En 30 segundos

Para trabajar en paralelo tenés dos niveles. Dentro de una sesión, Claude delega a subagents. Entre sesiones, corrés varios claude a la vez, cada uno en su propio git worktree (claude -w nombre) para que ninguno edite los archivos del otro. Para despachar y monitorear muchas sesiones desde una pantalla está claude agents.

Qué es y cómo funciona

El problema de correr dos sesiones de Claude sobre la misma carpeta: las dos editan los mismos archivos, una rompe lo que la otra está probando y los diffs se mezclan.

Un git worktree resuelve eso: es otro directorio de trabajo, con su propia rama y sus propios archivos, que comparte el historial y el remoto con tu checkout principal. Dos sesiones en dos worktrees nunca se pisan los archivos; después mergeás las ramas como siempre.

Las opciones, de menor a mayor escala
OpciónQué esCuándo
SubagentsWorkers dentro de una sesión; devuelven un resumenInvestigar varias cosas a la vez, aislar output ruidoso
/subtaskUn subagent que hereda toda tu conversación y corre en backgroundUna tarea lateral que necesita todo el contexto actual
claude -w <nombre>Una sesión en su propio worktreeDos o tres features/bugs en paralelo que manejás vos
Agent view (claude agents)Una pantalla para despachar y vigilar sesiones en background. Research previewVarias tareas independientes que querés "tirar" y revisar después
/batch <instrucción>Skill incluida: parte un cambio grande en 5–30 unidades, cada una en un subagent con su worktreeMigraciones masivas y mecánicas
Agent teamsVarias sesiones coordinadas por un líder, con tareas compartidas. Experimental, apagado por defectoTrabajo que necesita que los workers se hablen entre sí

Cómo se usa

Una sesión por worktree con --worktree
claude --worktree fix-ingesta-ventas     # o: claude -w fix-ingesta-ventas

Claude Code crea .claude/worktrees/fix-ingesta-ventas/ en la raíz del repo, en una rama nueva worktree-fix-ingesta-ventas que sale de la rama por defecto del remoto (normalmente main). En otra terminal:

claude -w modelo-dim-clientes

Y ya tenés dos sesiones aisladas. Otras variantes:

claude -w                       # nombre generado automáticamente
claude -w "#231"                # worktree a partir del PR #231 (comillas por el #)
claude -w fix-ingesta --tmux    # además abre una sesión de tmux para el worktree

Al salir, si el worktree no tiene cambios se borra solo; si tiene trabajo, Claude te pregunta si conservarlo y te imprime el comando para retomarlo (claude --worktree <nombre> --resume).

También podés pedírselo en medio de una sesión: "trabajá en un worktree".

Preparar el entorno de cada worktree

Un worktree es un checkout limpio: no tiene tu .venv, ni tu .env, ni target/ de dbt.

  • Archivos gitignoreados que necesitás copiar (.env, credenciales locales): listalos en .worktreeinclude en la raíz del repo, con sintaxis de .gitignore.
    .env
.env.local
  • Dependencias: pedile a Claude que las instale al empezar, o hacelo vos (uv sync, pip install -r requirements.txt, dbt deps).
  • Agregá .claude/worktrees/ a tu .gitignore para que no aparezcan como archivos sin trackear.
  • Si querés que los worktrees salgan de tu rama actual (con commits sin pushear) en vez de main, en settings: {"worktree": {"baseRef": "head"}}.
Worktrees a mano

Para salir de una rama existente o ubicar el worktree fuera del repo:

git worktree add ../datos-fix-dag -b fix/dag-ventas     # rama nueva
git worktree add ../datos-revision feature/nuevo-modelo  # rama existente
cd ../datos-fix-dag && claude

git worktree list
git worktree remove ../datos-fix-dag
Sesiones en background con agent view
claude agents                                            # abre la pantalla de agentes
claude --bg "investigá por qué falla el test test_dedupe_ventas"
claude --bg --name backfill-plan "proponé un plan de backfill para raw.eventos de septiembre"
claude --agent revisor-dbt --bg "revisá los modelos tocados en la rama feature/costos"

En agent view escribís un prompt y Enter despacha una sesión nueva; Espacio espía la última salida y te deja responder; Enter o → te mete en la sesión completa; ← vuelve a la tabla. Desde una sesión normal, /bg (o ← con el prompt vacío) la manda a background.

Las sesiones en background se mueven solas a un worktree propio antes de editar archivos, y al terminar commitean y pushean su rama (nunca a main, nunca force-push), salvo que tu CLAUDE.md diga que de git te encargás vos.

Subagents en paralelo y con worktree
Usá subagents en paralelo, cada uno en su propio worktree, para agregar tests de pytest a los tres DAGs de dags/ingesta/.

O fijalo en el subagent con isolation: worktree en su frontmatter. Y para cambios masivos:

/batch migrá todos los DAGs de dags/ de PythonOperator con provide_context a la TaskFlow API (@task)

/batch investiga, propone un plan con las unidades de trabajo, y cuando lo aprobás lanza un subagent por unidad, cada uno en su worktree, que implementa, corre tests y publica su cambio.

Ejemplo: una mañana con tres frentes abiertos

# Terminal 1: bug urgente en producción
claude -w fix-dup-ventas
> El DAG ingesta_ventas duplica filas desde el PR #231. Encontrá la causa, arreglalo y agregá un test.

# Terminal 2: feature nueva
claude -w dim-clientes-scd2
> Convertí dim_clientes en un snapshot SCD2 de dbt. Primero proponé el plan.

# Terminal 3 (o agent view): tarea larga que no necesita supervisión
claude --bg --name auditoria-costos "Listá los 20 modelos dbt que más bytes escanean según bq query --dry_run y proponé mejoras de partición/cluster. Solo lectura."

Mientras tanto vos revisás el plan de la terminal 2. Cuando el bug está listo, revisás el diff de esa rama, abrís el PR y cerrás la sesión.

Trucos y errores comunes

Trucos
  • Paralelo multiplica tokens. Diez sesiones gastan cuota más o menos diez veces más rápido que una. Empezá con 2–3.
  • Dividí por archivos, no por "temas". Aunque cada sesión tenga su worktree, si dos ramas tocan el mismo modelo vas a tener conflictos al mergear. Asigná a cada sesión un conjunto de archivos distinto.
  • Lo que sí comparten: el .git, los plugins de scope project, las aprobaciones de permisos ("no preguntar de nuevo" se guarda en el checkout principal) y las skills/agentes de .claude/ si el worktree no tiene su propia carpeta.
  • Hooks en worktrees: $CLAUDE_PROJECT_DIR sigue apuntando al checkout principal; si tu hook necesita el directorio del worktree, leé el campo cwd del JSON de entrada.
  • Agent view borra el worktree al borrar la sesión: commiteá antes de borrar una sesión que editó archivos.
  • Agent teams se habilitan con CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 en el env de settings. Gastan bastante más que subagents y no aíslan con worktrees: probalos solo para trabajo que realmente necesita coordinación entre workers.
  • ¿Querés otro modelo como segunda opinión en paralelo? Ver Multi-agente con Gemini.
Cuidado
  • Los worktrees no comparten .venv ni target/: cada uno necesita su setup. Sumá el comando de setup a CLAUDE.md para que Claude lo corra solo.
  • Corridas claude -p -w no se limpian solas: borrá esos worktrees con git worktree remove (y git worktree unlock si git se queja).

Como nadie aprueba permisos sobre la marcha, todo lo que Claude pueda hacer tiene que estar autorizado de antemano.

Ejemplo 2: revisar PRs de dbt en CI con GitHub Actions

Setup rápido

En una sesión dentro del repo:

/install-github-app

Instala la GitHub App de Claude en el repo, guarda el secret (ANTHROPIC_API_KEY, o CLAUDE_CODE_OAUTH_TOKEN si usás tu suscripción) y abre un PR con los workflows. Con eso, mencionar @claude en un PR o issue ya funciona. Requiere gh autenticado y permisos de admin en el repo; solo github.com.

Workflow que revisa solo cambios en models/

.github/workflows/revision-dbt.yml:

name: Revisión de modelos dbt
on:
  pull_request:
    types: [opened, synchronize, ready_for_review]
    paths:
      - "models/**"

jobs:
  revisar:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Revisá los modelos dbt modificados en este PR.
            Obtené el diff con: git diff origin/${{ github.base_ref }}...HEAD -- models/
            Buscá: joins que dupliquen filas respecto del grano, PK sin tests unique/not_null,
            select *, refs hardcodeadas en vez de ref()/source(), incrementales sin unique_key
            o sin filtro is_incremental().
            Dejá un comentario inline por cada problema, con qué pasaría en producción.
            Si no hay problemas, no comentes nada.
          claude_args: |
            --max-turns 15
            --allowedTools "Read,Grep,Glob,Bash(git diff *),mcp__github_inline_comment__create_inline_comment"
  • Con prompt, la action corre en modo automatización (no espera un @claude).
  • --allowedTools acota lo que puede hacer y, además, es lo que habilita la tool de comentarios inline.
  • Las reglas del equipo van en el CLAUDE.md del repo: la action lo lee en cada corrida.
  • Si ya tenés una skill de revisión en .claude/skills/, podés pasar prompt: "/revisar-modelo-dbt" directamente.
  • Para revisiones automáticas sin mantener un workflow, también existe el producto Code Review y el comando /code-review.

Tareas programadas

/loop: repetir algo mientras la sesión está abierta

  • Las tareas recurrentes expiran a los 7 días.

Corre aunque tu máquina esté apagada. Se gestionan en claude.ai/code/routines o con /schedule. Está en research preview, para planes Pro, Max, Team y Enterprise, con intervalo mínimo de 1 hora.

Si querés construir tu propio agente (un bot de on-call que mira alertas, un servicio que valida contratos de datos), el Claude Agent SDK te da el mismo loop agéntico, tools, permisos, hooks, subagents y MCP de Claude Code como librería de Python (pip install claude-agent-sdk) o TypeScript (npm install @anthropic-ai/claude-agent-sdk). Lee también los .claude/ del proyecto, así que tus skills y CLAUDE.md funcionan igual.

La diferencia con claude -p es el control: en vez de parsear JSON de un subproceso, iterás mensajes tipados y podés aprobar tools con callbacks propios. Para scripts y CI, claude -p alcanza; el SDK conviene cuando el agente es parte de una aplicación. Se autentica con API key (no con login de claude.ai). Arrancá por el quickstart oficial.

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage


async def main():
    async for message in query(
        prompt="Revisá dags/ingesta_ventas.py y listá tasks sin retries configurados.",
        options=ClaudeAgentOptions(allowed_tools=["Read", "Grep", "Glob"]),
    ):
        if isinstance(message, ResultMessage):
            print(message.subtype)


asyncio.run(main())

Trucos y errores comunes

Trucos
  • Pasá los datos por stdin en vez de darle permisos. gh pr diff 231 | claude -p "…" no necesita que Claude pueda correr gh.
  • --allowedTools con espacio antes del *: Bash(git diff *) matchea git diff …; Bash(git diff*) también matchea git diff-index.
  • Ponele techo a todo: --max-turns, --max-budget-usd y timeout-minutes en el workflow. Un agente sin límite en CI es una factura sin límite.
  • --output-format json incluye total_cost_usd: logealo para saber cuánto cuesta cada corrida automatizada.
Cuidado
  • En -p no hay a quién preguntar. Lo que no esté pre-aprobado se niega. En CI combiná --permission-mode dontAsk con un --allowedTools mínimo.
  • Repos que no controlás: sin --bare, claude -p corre los hooks de .claude/settings.json y conecta los servers de .mcp.json del repo sin preguntar, aunque nunca hayas confiado en esa carpeta.
  • OAuth de MCP no funciona en headless: autenticá esos servers antes en una sesión interactiva.
  • Secrets: nunca en el workflow ni en el repo. ANTHROPIC_API_KEY como secret de GitHub; para varios repos, secret de organización con una API key (el token OAuth queda atado a la suscripción de quien lo generó).
  • /loop no sobrevive a cerrar la terminal. Si tiene que correr de verdad, usá una rutina, una tarea de Desktop o Actions.

Multi-agente: delegar tareas chicas a Gemini

En 30 segundos

Claude Code coordina y decide; Gemini (vía Antigravity CLI) hace tareas chicas de solo lectura —segundas opiniones, revisiones mecánicas, resúmenes— que Claude le delega desde la propia sesión con agy -p. Un modelo distinto aporta una mirada independiente sin ensuciar tu contexto principal.

Por qué sumar otro agente

Un subagent de Claude ya resuelve la mayoría de las delegaciones. Gemini suma valor en un caso puntual: una segunda opinión de otro modelo, con otros sesgos. Sirve para detectar cosas que Claude pasa por alto sobre su propio trabajo (términos inconsistentes, links rotos, explicaciones confusas).

Usá…Cuando…
Inline (Claude solo)Ya sabés qué hacer y dónde
SubagentExploración larga o tareas en paralelo con contexto de Claude
Gemini (agy -p)Querés una revisión independiente, de otro modelo, de solo lectura

Setup

Gemini CLI (gemini) ya no sirve para cuentas individuales: falla con IneligibleTierError y pide migrar a Antigravity. El reemplazo es Antigravity CLI (agy).

  1. Instalá Antigravity desde antigravity.google y verificá:
agy --help
agy models          # modelos disponibles (Gemini Flash/Pro, entre otros)
  1. Probá el modo headless:
agy -p "Leé GIT.md y resumilo en 3 bullets." --mode plan --model gemini-3.8-flash-medium

Flags clave:

FlagPara qué
-p "<prompt>"Modo no interactivo: corre un prompt e imprime la respuesta
--mode planSolo lectura: lee el repo pero no edita (si le pedís un cambio, devuelve un plan)
--model <id>Flash para tareas rápidas; Pro para razonamiento más profundo
--print-timeout 5mCorta si tarda demasiado
--output-format jsonSalida estructurada si la vas a procesar con un script

Antigravity lee AGENTS.md de forma nativa, así que conoce las reglas del repo sin configuración extra.

Cómo se usa desde Claude Code

El repo trae la skill delegar-a-gemini, con un wrapper que fija modo solo lectura, modelo y timeout:

.claude/skills/delegar-a-gemini/scripts/gemini.sh "Leé docs/13-mcp.md y marcá afirmaciones que no estén respaldadas por un comando o config concreta."

En la práctica le hablás a Claude y él la invoca:

> pasale a Gemini una revisión de términos de docs/10-skills.md y docs/11-subagents.md
> pedile a Gemini segunda opinión sobre models/staging/stg_ventas.sql: ¿hay algo que rompa el incremental?

Para revisiones que querés procesar después, guardalas en el buzón:

.claude/skills/delegar-a-gemini/scripts/gemini.sh -o .agents/inbox/2026-10-02-revision-terminos.md "..."

Claude revisa .agents/inbox/ al empezar a trabajar, incorpora lo que vale la pena y borra el archivo (ver AGENTS.md).

Ejemplo: revisión cruzada de un modelo dbt

> Escribí el modelo incremental fct_ventas_diarias. Cuando termines, pasale a Gemini
  el SQL y el schema.yml para que busque problemas con el is_incremental() y la
  unique_key. Traeme sus observaciones y decidí cuáles aplicar.

Claude escribe el modelo, delega la revisión (solo lectura), evalúa las observaciones y aplica las que correspondan. Vos ves un solo hilo.

Trucos y errores comunes

Trucos
  • El prompt tiene que ser autocontenido. Gemini no ve tu conversación con Claude: pasale rutas, qué buscar y el formato de respuesta.
  • En headless no puede correr comandos. Si Gemini intenta un grep o ls, se lo niegan automáticamente y termina sin respuesta ("response": "" con denied_actions en la salida JSON). El wrapper le indica que solo lea archivos y avisa si la respuesta viene vacía. Nombrale los archivos exactos en vez de pedirle que "busque en todo el repo".
  • Tareas chicas. Cada llamada tarda ~30–60 s con Flash. Si algo necesita ida y vuelta, no es para Gemini.
  • Solo lectura siempre. Si los dos agentes editan, se pisan. Gemini propone, Claude aplica.
  • Para tareas largas, pedile a Claude que lo corra en background y siga con otra cosa.
Cuidado
  • No le creas a ciegas sobre Claude Code. Gemini puede no conocer comandos recientes; lo que proponga sobre features de Claude Code verificalo contra la doc oficial.

Arquitecturas de integración

En 30 segundos

Claude Code se puede usar en cuatro modos: interactivo en tu terminal, en paralelo/background, como script headless y dentro de CI o en la nube. La diferencia clave entre ellos es quién confirma las acciones riesgosas y cuándo. Empezá siempre interactivo y automatizá recién cuando el comportamiento es predecible.

Los cuatro modos

ModoCómo se veQuién aprueba accionesDetalle en
Interactivo localclaude en el repo, ida y vueltaVos, sobre la marchaFlujos de trabajo

CI / nubeGitHub Actions, rutinas (/schedule)Nadie, y además corre con credenciales compartidasAutomatización

La diferencia que importa: quién confirma

  • Con una persona presente, el sistema de permisos puede preguntar cuando hace falta. Preguntar es barato.
  • Sin nadie mirando, lo que no esté pre-aprobado se niega (o, si configuraste mal, se permite de más). Todo tiene que estar definido antes: allowlist mínima, deny de lo destructivo, topes de turnos y gasto.

Por eso cuanto más a la derecha de la tabla, más conservador hay que ser con el alcance.

Camino recomendado

  1. Interactivo: hacé la tarea a mano con Claude varias veces. Anotá qué permisos necesitó y qué salió mal.
  2. Empaquetá: convertí el procedimiento en una skill y las reglas críticas en hooks.
  3. Script: corré la skill con claude -p "/mi-skill" y permisos explícitos. Verificá que el output sea estable.
  4. CI o nube: recién ahí colgalo de un PR, un cron o una rutina.

Estructura de proyecto para sacarle el jugo

En 30 segundos

Claude Code funciona en cualquier repo, pero rinde mucho más si el repo le dice cómo testear, qué convenciones seguir y qué no tocar. Eso vive en CLAUDE.md, .claude/ y .mcp.json: se commitea para el equipo, y lo personal queda afuera.

Qué es / cómo funciona

Al abrir una sesión, Claude Code lee la configuración en capas:

  1. Memoria (CLAUDE.md): se carga entera al arrancar. Los CLAUDE.md de subcarpetas se cargan cuando Claude lee archivos de esa carpeta.
  2. Settings (.claude/settings.json y compañía): permisos, hooks, variables de entorno. Se combinan por precedencia y las listas se suman.
  3. Extensiones: skills, subagents, servers MCP. De cada skill y subagent solo se carga la description hasta que se usa.

Lo que hace rendir a un repo, además de esa config:

  • Comandos de test/lint estándar y que funcionen (uv run pytest, dbt build --select ...). Si una persona no puede correr los tests siguiendo el README, Claude tampoco.
  • Convenciones consistentes: un repo con un solo estilo se "lee" mejor que uno con tres mezclados.
  • Una forma de verificar: tests, dbt build, un dry run. Es lo que le permite a Claude saber si terminó.

Cómo se usa

Trucos y errores comunes

Trucos
  • CLAUDE.md gigante: si tiene cientos de líneas, Claude ignora la mitad. Movelo a rules/ con paths: o a skills. /context muestra cuánto pesa.
  • Mezclar contexto permanente con la tarea de hoy: "hoy migramos X" no va en CLAUDE.md; va en el prompt o en un SPEC.md que se borra al terminar.
  • Convenciones que solo están en la cabeza del equipo: si no está escrito, Claude no lo sabe (y una persona nueva tampoco).
  • Archivos llamados CLAUDE.md en carpetas de ejemplos o fixtures: se cargan cuando Claude entra ahí. Por eso los ejemplos de esta wiki tienen otro nombre.
  • Probá la config: /permissions, /hooks, /skills, /mcp y /context muestran qué cargó y de dónde. claude doctor valida los settings.
Cuidado
  • No versionar .claude/: cada uno rearma lo mismo y el agente se comporta distinto según quién lo use. Commiteá todo menos settings.local.json y CLAUDE.local.md.
  • Secretos en .mcp.json: usá ${VAR} y que cada uno exporte la suya.
  • .claudeignore no existe: para que Claude no lea algo, deny con Read(...) en settings.

Flujos de trabajo para el día a día

En 30 segundos

Casi todo flujo bueno es el mismo esqueleto: explorar → planificar → implementar con verificación → revisar el diff → commitear, con /clear entre tareas. Abajo, cinco recetas concretas del stack de datos con los prompts tal cual.

Qué es / cómo funciona

El esqueleto y cuándo saltear pasos:

PasoHerramientaSaltealo si...
ExplorarPreguntas directas, @archivo, subagent para búsquedas abiertasYa sabés exactamente qué archivo y qué cambio
PlanificarPlan mode (Shift+Tab o /plan), Ctrl+G para editar el planEl cambio entra en una frase (renombre, typo, una línea)
ImplementarModo default o acceptEdits—
VerificarTests, dbt build, dry run, airflow dags testNunca
Revisar/diff, /code-review, subagent revisorNunca para algo que va a prod

Regla práctica para el plan: si al leer el pedido en voz alta hay más de una forma razonable de resolverlo, planeá primero.

Cómo se usa

Antes de cualquier receta: rama nueva, sesión limpia.

git switch -c fix/duplicados-ventas
claude -n duplicados-ventas
1. Onboarding a un repo que no conocés
Explicame este repo como si fuera mi primer día: qué hace, cómo está organizado,
de dónde vienen los datos y adónde van, cómo se corren los tests. No modifiques nada.

Seguí con preguntas puntuales ("¿qué DAG escribe en raw.pagos?", "¿por qué fct_ventas es incremental?"). Cuando entiendas el repo: /init para generar un CLAUDE.md base y podalo a mano. Ideal en plan mode: lee todo y no toca nada.

2. Bugfix con test primero
En fct_ventas hay order_id duplicados desde el 3/10 (ver query abajo).
1. Escribí un test singular en tests/ que reproduzca el problema y mostrame que falla.
2. Encontrá la causa (sospecho del join con stg_pagos, pero verificalo).
3. Arreglalo sin DISTINCT y mostrame que el test pasa con
   dbt build --select fct_ventas+ --target dev.

Si a la segunda corrección sigue errado: /clear y reescribí el prompt con lo aprendido.

3. Nuevo modelo dbt

Con la skill dbt-nuevo-modelo instalada:

/dbt-nuevo-modelo stg_crm__clientes staging

Sin la skill, el mismo pedido explícito: fuente, grano, PK, materialización, tests, y "validá con dbt compile + dry run, no corras dbt run". Cerrá con @agent-revisor-dbt revisá stg_crm__clientes.

4. Revisar un PR
Revisá el PR 142 (gh pr diff 142). Enfocate en correctitud de los datos:
granularidad, joins que multiplican filas, filtros de partición, tests faltantes.
Ignorá estilo. Para cada hallazgo: archivo:línea, qué se rompe y cómo arreglarlo.

Alternativas: /code-review 142 (subagent con contexto limpio), /security-review para la rama actual. Si tenés el MCP de GitHub, Claude puede dejar los comentarios en el PR, pero que lo haga después de que vos leas los hallazgos.

5. Debug de un DAG que falló
El DAG ingesta_ventas falló anoche en la task cargar_bq. Log abajo.
Usá un subagent para leer el DAG, el SQL de la task y los helpers de dags/common que use,
y devolveme: causa más probable, evidencia, y cómo reproducirlo con
airflow tasks test. No cambies nada todavía.

<pegá acá el log de Composer>

Después: test que reproduzca → fix → uv run pytest tests/test_dag_integrity.py → diff. Caso completo en casos de uso.

Ejemplo

Una tarde típica con tres tareas, sin arrastrar contexto:

> [tarea 1] fix de duplicados con test primero (receta 2)
> commiteá con un mensaje que explique la causa
> /rename fix-duplicados-ventas
> /clear
> [tarea 2] /dbt-nuevo-modelo fct_cobranzas marts
> @agent-revisor-dbt revisá fct_cobranzas
> /clear
> [tarea 3] /btw ¿qué hacía require_partition_filter?   ← no ensucia el historial

Trucos y errores comunes

Trucos
  • Contexto completo de entrada: log real, archivo con @, qué ya probaste. Ahorra vueltas.
  • Pasos verificables: un modelo, dbt build, el siguiente. Corregir después de un paso chico es barato.
  • Esc apenas ves que se desvía; Esc Esc / /rewind para volver. Los checkpoints no cubren lo que cambió un comando de Bash: para eso, git.
  • Exploración en paralelo: "en paralelo, con subagents: ..." cuando las preguntas no dependen entre sí. Para trabajar en dos ramas a la vez: claude -w nombre (15).
  • Spec para lo grande: que te entreviste, escriba SPEC.md, /clear, e implemente otra sesión leyendo la spec.
  • Tareas repetitivas → skill. Si escribiste el mismo prompt largo tres veces, es una skill (10).
  • Autonomía según confianza: acceptEdits en un repo que conocés y con buena allowlist; default en uno nuevo.
Cuidado
  • "Compiló" no es "está bien": cerrá el loop con la verificación real y el diff.

Costos

En 30 segundos

Claude Code cobra por tokens. Cada mensaje reenvía toda la conversación (cacheada, pero se cobra igual), así que lo que más gasta es contexto largo, no la pregunta en sí. Medilo con /usage y la status line; ahorrá con /clear, el modelo justo, subagents para lo verboso y CLI antes que MCP.

Qué es / cómo funciona

Cómo se cobra
Si usás...Cómo pagásDónde mirás
Suscripción (Pro, Max, Team, Enterprise)Incluido en el plan, con límites por ventana de 5 horas y semanal. Pasado el límite, usage credits si están habilitados/usage (barras del plan)
API key (Claude Console)Por token, a precio de lista/usage (estimado) y la página Usage de la Console (lo real)
Google Cloud (Agent Platform / Vertex), Bedrock, FoundryPor token, a tu cuenta de la nubeBilling del proveedor (Claude Code no le reporta a Anthropic)

Referencia oficial: en empresas, el promedio ronda los USD 13 por developer por día activo (USD 150–250 por mes), y el 90 % queda debajo de USD 30 por día.

Qué gasta tokens
  • El contexto entero, en cada request. Cada mensaje y cada tanda de resultados de tools manda toda la conversación. El prompt caching lo abarata (lee a tarifa de cache), pero una pregunta de una línea en una sesión abierta todo el día "carga" todo el día.
  • Cache misses. Después de una pausa más larga que la vida del cache (1 hora en suscripción; 5 minutos por API o usando usage credits), el primer mensaje reprocesa todo el contexto a precio completo.
  • Thinking. El razonamiento extendido se cobra como output y puede ser decenas de miles de tokens por request.
  • Subagents, workflows y agent teams. Cada uno hace sus propias requests. Los agent teams usan ~7x más tokens que una sesión normal.
  • Lo que leés. Archivos enteros, logs, salidas de comandos largas: todo queda en el contexto.
  • MCP. Las definiciones de tools se cargan diferidas (solo nombres hasta que se usan), pero cada server suma algo; un CLI (bq, gcloud, gh) no suma nada hasta que se corre.
  • /compact. Lee toda la conversación para resumirla: es una request grande. /clear no cuesta nada.
  • Cosas que corren solas. /loop, tareas programadas y goals mandan el contexto completo en cada disparo. En background hay un consumo chico (resúmenes para --resume, sugerencias de prompt): típicamente menos de USD 0,04 por sesión.

Cómo se usa

/usage (alias /cost y /stats)

Muestra el costo estimado de la sesión, tokens por modelo, estadísticas del prompt cache y, en planes de suscripción, las barras de límite y un desglose de qué consumió (skills, subagents, MCP). El monto en dólares es un estimado a precio de lista calculado localmente; se resetea con /clear. Para suscriptores, ese monto no es lo que pagás: mirá las barras.

Status line con costo y contexto

/statusline y describí lo que querés ("modelo, % de contexto y costo"), o armala a mano en ~/.claude/settings.json:

{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh"
  }
}

~/.claude/statusline.sh (chmod +x):

#!/bin/bash
input=$(cat)
modelo=$(jq -r '.model.display_name' <<<"$input")
ctx=$(jq -r '.context_window.used_percentage // 0 | floor' <<<"$input")
costo=$(jq -r '.cost.total_cost_usd // 0' <<<"$input")
limite5h=$(jq -r '.rate_limits.five_hour.used_percentage // empty | floor' <<<"$input")

linea="[$modelo] ctx ${ctx}% | \$$(printf '%.2f' "$costo")"
[ -n "$limite5h" ] && linea="$linea | 5h ${limite5h}%"
echo "$linea"

Campos útiles que recibe el script: cost.total_cost_usd, context_window.used_percentage, rate_limits.five_hour.used_percentage / seven_day (planes de suscripción), model.display_name, effort.level.

Trucos y errores comunes

Trucos
  • /clear entre tareas es el ahorro número uno. /rename antes para poder volver con /resume.
  • /context te muestra qué está comiendo el context window (archivos, MCP, memoria, skills).
  • CLAUDE.md corto: se carga en cada sesión. Lo específico, a skills (se cargan solo cuando se usan). /skill-doctor muestra cuánto contexto ocupa cada skill.
  • Modelo por tarea: default para el día a día, opus para lo difícil, model: haiku en subagents mecánicos. Cambiar a Opus también cambia los subagents que heredan el modelo.
  • Bajá el esfuerzo con /effort en tareas simples: el thinking se cobra como output.
  • Prompts específicos: "mejorá el repo" dispara lectura masiva; "agregá un test unique a order_id en fct_ventas.yml" lee dos archivos.
  • Corregí temprano con Esc: cada paso en la dirección equivocada se paga dos veces (ir y deshacer).
  • Instrucciones de compactación en CLAUDE.md ("al compactar, conservá la lista de archivos modificados y los comandos de test") para que /compact no pierda lo importante.
  • El otro costo: BigQuery. Que Claude corra bq query sin mirar cuesta más que los tokens. Allowlist para --dry_run, confirmación para lo real (guardia de BigQuery) y BIGQUERY_MAXIMUM_BYTES_BILLED en el MCP.
Cuidado
  • No dejes la sesión idle una hora y volvé con una pregunta chica: el cache expiró y reprocesa todo. Si es otro tema, /clear.
