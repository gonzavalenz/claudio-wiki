Fundamentos: LLM, agente y el bucle agéntico

Lo mínimo para entender de qué está hecho todo lo demás.

Un LLM (modelo de lenguaje grande) predice texto: dado un contexto, genera la continuación más probable. Un chat común se queda ahí — vos escribís, el modelo responde en texto, listo. Un agente es distinto: además de responder en texto, puede decidir usar herramientas (leer un archivo, correr un comando, hacer una consulta SQL) y ver el resultado antes de seguir.

Claude Code es un agente. Cuando le pedís "revisá por qué el pipeline de ventas está tardando el doble", no te devuelve una hipótesis genérica: abre el archivo del DAG, corre bq query para ver el plan de ejecución, lee los logs, y recién ahí te contesta con algo basado en lo que encontró.

// el bucle agéntico, simplificado
1. vos escribís un objetivo
2. el modelo decide: ¿respondo, o uso una herramienta?
3. si usa una herramienta → ve el resultado real
4. vuelve a 2, hasta que el objetivo está resuelto

Este bucle es la diferencia entre "pedile código a un chat y pegalo vos" y "dale un objetivo y que investigue, ejecute y verifique". Todo lo que sigue en esta guía — skills, subagents, hooks, MCP — son formas distintas de darle más contexto, más herramientas o más estructura a ese mismo bucle.

~/equipo-datos $ cat 02-que-es.md

Qué es Claude Code y dónde vive

La misma herramienta, varias puertas de entrada.

Claude Code es la terminal agéntica de Anthropic: se instala como CLI, corre en tu máquina (o en la nube), y trabaja directamente sobre tus archivos reales — no sobre copias pegadas en un chat. Lee tu repo, entiende la estructura del proyecto, ejecuta comandos, edita archivos y hace commits, siempre pidiendo tu aprobación según el modo de permisos activo.

Superficies disponibles

SuperficieCuándo conviene
Terminal / CLIEl uso base — iTerm2, cualquier shell. La más flexible, la que usa el resto de esta guía.
VS Code / JetBrainsVer diffs inline, mantener el contexto del editor mientras Claude edita.
Claude Code en la webLanzar tareas largas (una migración, un refactor grande) sin depender de que tu laptop esté prendida.
Desktop appVarias sesiones en paralelo, vista de diffs, sesiones remotas por SSH.
SlackConsultas rápidas del equipo sin abrir una terminal — bueno para preguntas puntuales, no para trabajo profundo.

Lo que puede hacer por sí solo: leer y editar archivos, ejecutar comandos de shell, buscar en la web, y — vía MCP — conectarse a herramientas externas como BigQuery, Google Drive, Jira o Slack. La diferencia central frente a pegar código en un chat es esa: actúa sobre el entorno real y ve el resultado, en vez de solo describir qué harías.

Para arrancar

Si el equipo nunca usó Claude Code, empiecen todos por la terminal. Es la superficie donde se entiende mejor qué está pasando (qué comando corrió, qué archivo tocó) antes de sumar la comodidad del editor.

Modelos: cuál usar para qué

Claude Code no corre un solo modelo — vos elegís el balance entre velocidad, costo y profundidad de razonamiento en cada momento.

En vez de nombres de versión, Claude Code usa alias que siempre apuntan al modelo recomendado de esa familia. Así el equipo no tiene que memorizar números de versión, y las guías internas no quedan desactualizadas cuando Anthropic libera un modelo nuevo.

AliasPara qué
haikuRápido y barato. Tareas mecánicas: renombrar columnas en 40 archivos, generar boilerplate de tests, formatear.
sonnetEl caballo de batalla diario. Escribir queries, modelos de dbt, revisar un PR, debuggear un DAG.
opusRazonamiento profundo. Decisiones de arquitectura de un pipeline, un refactor que toca muchas dependencias, un bug esquivo.
fableEl más capaz, pensado para tareas largas y ambiguas: "investigá por qué el costo de BigQuery se disparó este mes" y dejarlo trabajar sin supervisión constante. No es el modelo por defecto — se activa a propósito.
opusplanHíbrido: usa Opus para planificar y Sonnet para ejecutar. Buen default cuando no querés pensar cuál elegir.

Se cambia en cualquier momento con /model (sin argumentos abre un selector), al arrancar con claude --model opus, o se fija un default en la configuración del proyecto. El cambio es inmediato y no pierde el contexto de la conversación.

$ claude --model opus // arrancar en Opus
> /model sonnet // cambiar a mitad de sesión

3.1Effort level: cuánto piensa antes de responder

Además del modelo, cada mensaje tiene un nivel de esfuerzo (low, medium, high, xhigh, max) que controla cuánto razona internamente antes de actuar. high es el default en casi todos los modelos y sirve para la mayoría del trabajo. Bajarlo con /effort medium ahorra tokens en tareas simples y repetitivas; subirlo a xhigh o escribir ultrathink en el prompt pide más profundidad para un problema puntual, sin cambiar la config de toda la sesión.

Regla práctica para el equipo

Arranquen con sonnet como default. Suban a opus cuando Sonnet se traba en algo con muchas piezas interconectadas (ej. un cambio que toca el pipeline, el modelo de dbt y el dashboard a la vez). Bajen a haiku para trabajo mecánico en volumen. fable queda para investigaciones abiertas donde vale la pena dejarlo trabajar más tiempo sin intervenir.

Cinco minutos, una sola vez por máquina.

claude --version

La primera vez pide autenticarse contra tu cuenta de Claude (o contra la API key de la organización, según cómo esté configurado el acceso del equipo). Una vez adentro, la sesión ya tiene acceso de lectura a los archivos del directorio actual — probar con algo simple primero:

> ¿Qué hace este repo? Dame un resumen de la estructura.

Memoria: que no tengas que reexplicar el proyecto cada vez

Dos sistemas complementarios, uno que vos escribís y otro que Claude escribe solo.

CLAUDE.md es un archivo markdown que se carga entero al arrancar cada sesión y queda en contexto durante toda la conversación. Ahí van las reglas fijas: convenciones de nombres de tablas, cómo correr los tests, qué NO tocar. Se puede tener en varios niveles — uno por proyecto (compartido vía git), uno personal en ~/.claude/CLAUDE.md (aplica a todos tus proyectos), y uno de organización si el equipo lo administra centralizado.

# CLAUDE.md — pipelines/ventas-diarias

## Stack
- Python 3.11, orquestado con Airflow. Modelos SQL en dbt.
- BigQuery: dataset `ventas_prod` es de solo lectura para todos
  excepto el service account de Airflow.

## Convenciones
- Nombres de tabla: `snake_case`, prefijo por dominio (`ventas_`, `stock_`).
- Nunca corras queries sin `LIMIT` en `ventas_prod` para explorar —
  usá `ventas_staging`, tiene los mismos datos con TTL de 7 días.

## Comandos
- Tests: `pytest tests/ -x`
- Compilar modelos dbt: `dbt build --select +modelo_afectado`

@docs/esquema-datasets.md

La última línea es un import: con @ruta/al/archivo.md se puede traer contenido de otro documento sin duplicarlo — útil para no repetir un esquema de datos largo en cada CLAUDE.md del monorepo. Si las reglas varían por carpeta (por ejemplo, otras convenciones para /notebooks que para /pipelines), .claude/rules/ permite reglas específicas por path en vez de un único archivo gigante.

Auto memory es distinto: Claude va guardando notas propias a medida que trabaja — comandos que le corregiste, decisiones de arquitectura, hábitos de debugging — sin que se lo pidas. Está activada por default y es personal (no se comparte por git). Con /memory se ve qué archivos de memoria están cargados en la sesión actual y se puede auditar o editar lo que Claude anotó.

Regla de oro

CLAUDE.md se lee entero en cada mensaje de la sesión — cada línea de más cuesta tokens en cada turno. Manténganlo corto y con reglas duras (lo que Claude debe hacer siempre), y usen un skill para procedimientos largos que solo se cargan cuando hacen falta.

6.1Comandos propios del equipo

Además de los comandos incorporados, se pueden crear comandos a medida — por ejemplo /nueva-migracion que siempre siga los mismos pasos para agregar una tabla nueva al warehouse. Hoy la forma recomendada de crearlos es como skill (ver la próxima sección): un archivo markdown en .claude/skills/nombre/SKILL.md que se invoca igual, con /nombre, pero además soporta argumentos, archivos de apoyo y puede correr en un subagent aparte. La forma antigua — un archivo suelto en .claude/commands/ — sigue funcionando, así que no hace falta migrar nada existente.

Permisos: cuánto autonomía le das

Esto es lo primero que hay que entender bien antes de dejar que Claude Code toque algo cerca de datos productivos.

ModoQué haceCuándo usarlo
defaultPregunta antes de cada edición o comando.Trabajo cerca de datos sensibles o producción.
planSolo investiga y propone un plan — no edita nada hasta que lo aprobás.Explorar un pipeline nuevo o encarar un cambio grande antes de tocar código.
acceptEditsEdita archivos sin preguntar cada vez; vos revisás con git diff después.Iteración rápida en una rama propia, con git como red de seguridad.
autoUn clasificador aprueba automáticamente lo que considera seguro (lecturas, búsquedas) y sigue preguntando lo riesgoso.Sesiones largas de refactor donde aprobar cada paso cansa.

Para datos de clientes

Si el proyecto toca datasets con información personal, conviene declarar explícitamente en settings.json qué credenciales y qué datasets están fuera de alcance (deny sobre el service account de escritura en prod, por ejemplo), en vez de confiar solo en que el modo de permisos por defecto alcance. Un hook que bloquee queries sin LIMIT contra ventas_prod es más confiable que pedírselo por CLAUDE.md.

Skills: empaquetar conocimiento y procedimientos

La forma de decirle a Claude "así hacemos las cosas acá" sin repetirlo cada vez.

Un skill es una carpeta con un archivo SKILL.md: un encabezado YAML que le dice a Claude cuándo usarlo, y contenido markdown con las instrucciones. Se activa solo — cuando tu pedido coincide con la description — o a mano con /nombre-del-skill. La diferencia clave con CLAUDE.md es que el contenido del skill no se carga en cada turno: solo entra en contexto la primera vez que se invoca, así que se puede meter documentación larga sin costo mientras no se use.

Creá uno cuando te das cuenta de que estás pegando la misma checklist o el mismo procedimiento en el chat una y otra vez.

~/.claude/skills/ // personal, todos tus proyectos
.claude/skills/ // del proyecto, se comparte por git

8.1Ejemplo — estándares de SQL como conocimiento de referencia

## .claude/skills/estandar-sql/SKILL.md
---
description: Convenciones de SQL para BigQuery de este equipo. Usar
  siempre que se escriba o revise una query o un modelo de dbt.
---

Al escribir SQL para BigQuery en este repo:
- CTEs con nombres descriptivos, no `t1`, `t2`.
- Particionar por `fecha` en tablas de hechos; clusterizar por
  `id_cliente` cuando la tabla se filtra por cliente seguido.
- Nunca `SELECT *` en un modelo de dbt que se materializa como tabla.

Esto no es una tarea que se "ejecuta": es contexto que Claude aplica solo cuando estás trabajando con SQL. No necesita disable-model-invocation ni argumentos — se activa solo.

8.2Ejemplo — un procedimiento con pasos, invocado a mano

## .claude/skills/nueva-tabla/SKILL.md
---
description: Agrega una tabla nueva al warehouse siguiendo el
  checklist del equipo.
disable-model-invocation: true
allowed-tools: Bash(dbt run *) Bash(dbt test *)
---

Dar de alta la tabla $ARGUMENTS:
1. Crear el modelo en `models/staging/` siguiendo el esquema de
   `models/staging/_schema.yml`.
2. Agregar tests de `not_null` y `unique` sobre la clave primaria.
3. Correr `dbt run --select +$ARGUMENTS` y `dbt test --select $ARGUMENTS`.
4. Documentar la tabla en `docs/esquema-datasets.md`.

disable-model-invocation: true significa que Claude nunca lo dispara solo — solo corre cuando alguien del equipo escribe /nueva-tabla ventas_devoluciones. Tiene sentido para acciones con efecto real, donde el timing lo decide una persona, no el modelo.

Contexto dinámico

Una línea como !`bq query --dry_run --format=json < query.sql` dentro de un skill ejecuta ese comando antes de que Claude vea el contenido, e inserta el resultado real (por ejemplo, los bytes que va a escanear la query) en el prompt. Útil para un skill de "estimá el costo de esta query antes de correrla".

~/equipo-datos $ cat 09-subagents.md

Subagents: delegar sin ensuciar la conversación principal

Un subagent arranca con contexto vacío, hace su tarea, y devuelve solo el resultado final.

Claude Code ya trae subagents incorporados que usa solo, sin que se los pidas: Explore (solo lectura, optimizado para buscar y entender código, corre rápido y barato), Plan (investiga durante el modo plan), y general-purpose (para tareas que mezclan exploración y edición). No hace falta invocarlos a mano — explican buena parte de lo que Claude ya hace "solo" internamente.

Además se pueden crear subagents propios: archivos markdown en .claude/agents/ con un rol fijo, herramientas restringidas y, opcionalmente, un modelo distinto al de la sesión principal.

## .claude/agents/validador-queries.md
---
name: validador-queries
description: Revisa una query de BigQuery antes de que se
  corra contra producción — costo estimado, particiones, riesgos.
tools: Read, Bash(bq *)
model: haiku
---

Sos un revisor de queries de BigQuery. Para cada query:
1. Corré `bq query --dry_run` y reportá los bytes escaneados.
2. Marcá si falta filtro de partición en tablas grandes.
3. Marcá cualquier `SELECT *` contra una tabla de más de 1TB.
Sé breve: una lista de hallazgos, no un ensayo.

¿Cuándo conviene un subagent en vez de resolverlo en la conversación principal? Cuando la tarea implica leer o generar mucho volumen que no necesitás ver en detalle — explorar 40 archivos para entender un pipeline legacy, por ejemplo — y solo te interesa el resumen final. El subagent absorbe ese ruido en su propia ventana de contexto; a la conversación principal solo vuelve la conclusión.

No es magia gratis

Un subagent arranca sin ver tu conversación previa — el único canal que tiene es el mensaje de delegación que Claude le escribe. Para tareas chicas (correr un comando, un cambio de una línea), delegar agrega más overhead del que ahorra. Resérvenlo para investigación real.

Hooks: reglas que no dependen de que el modelo se acuerde

CLAUDE.md es una sugerencia que Claude suele seguir. Un hook es determinístico: corre siempre.

Un hook es un comando de shell (o un prompt, o un subagent) que se ejecuta automáticamente en un punto fijo del ciclo de vida de la sesión — antes de correr una herramienta, después de editar un archivo, al iniciar la sesión, cuando Claude termina de responder. Se configuran en .claude/settings.json con un evento, un matcher (qué herramienta dispara el hook) y el comando a correr.

// .claude/settings.json — formatear SQL automáticamente
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit",
      "hooks": [{ "type": "command",
        "command": "sqlfluff format --dialect bigquery $CLAUDE_TOOL_INPUT_FILE_PATH" }]
    }]
  }
}

El caso de uso que más importa para un equipo de datos es el opuesto — bloquear algo antes de que pase. Un hook de PreToolUse que termina con código de salida 2 cancela la acción:

// bloquear cualquier escritura contra el dataset de producción
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": "./scripts/bloquear-prod.sh" }]
    }]
  }
}

Ese script recibe el comando propuesto por stdin en JSON; si detecta un bq query sin --dry_run apuntando a ventas_prod, sale con código 2 y Claude Code cancela la acción sin excepción — no importa qué diga el prompt, ni si Claude "decidió" que estaba bien.

La distinción que importa

CLAUDE.md dice "por favor no hagas esto" — el modelo generalmente lo respeta, pero es una instrucción, no una barrera. Un hook dice "esto no puede pasar" y lo garantiza a nivel de sistema. Para cualquier regla que no pueda romperse (no tocar prod, no exponer una credencial), usen un hook, no una línea en CLAUDE.md.

MCP: conectar herramientas y datos externos

El protocolo que le da a Claude acceso a lo que vive fuera del repo — bases de datos, Drive, Slack, Jira.

MCP (Model Context Protocol) es un estándar abierto para conectar un agente a servidores que exponen herramientas o datos. En la práctica: instalás un servidor MCP para BigQuery una vez, y a partir de ahí Claude puede listar datasets, inspeccionar esquemas y correr queries de lectura sin que copies y pegues nada — habla directo con la fuente.

# registrar un servidor MCP para BigQuery (MCP Toolbox for Databases, de Google Cloud)
claude mcp add bigquery -- ./toolbox --prebuilt bigquery --stdio

# o vía .mcp.json en la raíz del repo, para compartirlo con el equipo
// .mcp.json
{
  "mcpServers": {
    "bigquery": {
      "command": "./toolbox",
      "args": ["--prebuilt", "bigquery", "--stdio"],
      "env": { "BIGQUERY_PROJECT": "mi-proyecto-gcp" }
    }
  }
}

Un .mcp.json en la raíz del repo se versiona con git, así que todo el equipo arranca con los mismos servidores conectados al abrir el proyecto. Con /mcp se confirma que el servidor quedó conectado.

GitHub

Crear PRs, leer issues, comentar revisiones sin salir de la sesión.

Google Drive / Slack

Leer un doc de especificación o el hilo de Slack donde se discutió un requerimiento.

Postgres / otras bases

Mismo patrón que BigQuery — inspeccionar esquema y correr lecturas contra otra fuente del stack.

Sentry / monitoreo

Cruzar un error de producción con el código que lo generó, en la misma sesión.

Credenciales

Conecten el servidor de BigQuery con un usuario de solo lectura siempre que el objetivo sea explorar y escribir queries, no un service account con permisos de escritura sobre datasets productivos. MCP le da a Claude las mismas capacidades que tiene esa credencial — ni más, ni menos.

Arquitecturas de integración

Claude Code no es solo "una terminal que uso yo" — el mismo binario corre en CI, en un job programado, o disparado por un evento.

12.1Local e interactivo

El caso base: terminal o editor, alguien del equipo manejando la sesión en tiempo real. Es donde arranca todo el mundo y sigue siendo el modo correcto para el trabajo exploratorio y de diseño.

12.2CI/CD — modo headless

Con -p (print), Claude Code corre una vez, sin interfaz, y devuelve el resultado — se comporta como cualquier comando de Unix, componible con pipes y usable en un pipeline.

# pasar un diff y obtener una revisión en JSON
git diff origin/main | claude -p "Revisá este diff de SQL/dbt: riesgos de costo, falta de tests" \
  --output-format json > revision.json

Esto habilita, por ejemplo, un paso de GitHub Actions que revisa automáticamente cada PR que toca modelos de dbt, buscando SELECT * sin filtro de partición o falta de tests — y lo comenta en el PR antes de que lo revise una persona.

12.3Automatización con el Agent SDK

Para tareas recurrentes que no necesitan un humano en el loop, el Agent SDK (Python o TypeScript) permite que un script propio invoque a Claude Code programáticamente. Encaja con infraestructura simple — un Cloud Run Job o una Cloud Function que corre un validador de calidad de datos cada madrugada, en vez de sumar otro servicio administrado al stack.

// ejemplo de uso: detector de anomalías de costo
Cloud Scheduler (cron diario)
  → Cloud Run Job
    → script Python + Agent SDK
      → Claude revisa el costo de BigQuery del día anterior
      → si hay un salto anómalo, postea en Slack

12.4Tareas programadas y Claude Code en la web

Para algo más simple que un script del Agent SDK, /loop corre un prompt en un intervalo fijo dentro de una sesión. Para tareas largas que no dependen de tu laptop encendida, Claude Code en la web las corre en un entorno en la nube.

12.5Slack

Para consultas puntuales del equipo — "¿por qué falló el pipeline de anoche?" — sin que nadie tenga que abrir una terminal. Útil como puerta de entrada liviana, no como reemplazo del trabajo profundo en el editor.

Estructura de proyecto para sacarle el jugo

Todo lo de las secciones anteriores vive en un mismo lugar del repo, versionado junto con el código.

mi-repo/
├── CLAUDE.md // reglas del repo completo
├── .mcp.json // servidores MCP compartidos por el equipo
├── .claude/
│   ├── settings.json // permisos, hooks
│   ├── skills/
│   │   ├── estandar-sql/SKILL.md
│   │   └── nueva-tabla/SKILL.md
│   ├── agents/
│   │   └── validador-queries.md
│   └── hooks/
│      └── bloquear-prod.sh
├── pipelines/
├── dbt_models/
│   └── .claude/skills/ // skills que solo aplican a dbt_models/
├── notebooks/
└── terraform/

En un monorepo con carpetas de naturaleza distinta (pipelines de Airflow, modelos de dbt, notebooks de análisis, infraestructura en Terraform), un único CLAUDE.md gigante en la raíz se vuelve difícil de mantener. Claude Code también lee .claude/skills/ anidados: uno en dbt_models/ con las convenciones específicas de dbt se activa solo cuando Claude está trabajando ahí, sin ensuciar el contexto del resto del repo.

.mcp.json en la raíz, versionado, es lo que hace que todo el equipo se conecte a los mismos servidores (BigQuery, GitHub) sin configurar nada a mano — se lee automáticamente al abrir el proyecto.

13.1Plugins: empaquetar todo junto

Cuando el conjunto de skills, hooks, subagents y servidores MCP del equipo crece, un plugin los agrupa en una unidad instalable y versionada — en vez de que cada persona arme su propia configuración suelta a mano. Se distribuye desde un repositorio interno (un "marketplace" propio, no público) y se instala con un comando, lo que facilita mantener a todo el equipo alineado cuando cambian las convenciones.

Flujos de trabajo para el día a día

Casos concretos, con el prompt de arranque que funciona bien en cada uno.

14.1Entender un pipeline nuevo

Antes de tocar nada: "Explicame el flujo completo de este pipeline: de dónde saca los datos, qué transformaciones hace, dónde escribe el resultado. No cambies nada." — en modo plan, para que quede solo en investigación.

14.2Debuggear un DAG que falla

Pegar el log de error y pedir la causa raíz, no solo el fix: "Este DAG de Airflow falló anoche, este es el log. Encontrá la causa raíz antes de proponer un cambio." Claude va a leer el log, ir al código de la tarea que falló, y probablemente correr el mismo comando en un entorno de prueba antes de contestar.

14.3Migrar SQL entre dialectos

Por ejemplo, de un warehouse legacy a BigQuery. Dar un ejemplo migrado a mano primero ("así migramos la tabla X") ayuda mucho más que solo pedir "migrá todo" — Claude sigue el patrón establecido en vez de inventar uno propio archivo por archivo.

14.4Generar documentación

"Documentá cada tabla de models/marts/ en el schema.yml de dbt: qué representa cada columna, de dónde sale." — funciona mejor delegado a un subagent de exploración si son muchos modelos, para no llenar la conversación principal de contenido que no necesitás revisar línea por línea.

14.5Escribir tests

Para modelos de dbt: "Agregá tests de not_null, unique y un test de relación contra la tabla de dimensión, para el modelo fct_ventas." Para código Python: pedir primero los casos límite que se te ocurran a vos, después que Claude complete el resto — el resultado cubre mejor los casos que realmente importan.

14.6Code review de un PR

/review dispara una revisión de los cambios pendientes. Para un PR ya abierto en GitHub (con el MCP de GitHub conectado): "Revisá el PR #482: enfocate en riesgos de costo de las queries nuevas y falta de tests."

Costos y buenas prácticas

El consumo se mide en tokens: todo lo que entra en el contexto (tu prompt, el historial, los archivos leídos, el CLAUDE.md) y todo lo que Claude genera.

15.1Los tres hábitos que más importan

  • Elegir el modelo según la tarea — la decisión de mayor impacto en el costo. Ver la sección de modelos.
  • Cortar sesiones que no tienen relación entre sí con /clear, en vez de arrastrar una conversación larga hacia una tarea completamente distinta. Una sesión que llegó a 200K tokens reenvía todo ese contexto en cada mensaje nuevo.
  • Mantener CLAUDE.md corto — se lee entero en cada turno de cada sesión. Reglas duras y cortas ahí; procedimientos largos como skill, que solo carga cuando se usa.

15.2Cuándo NO usar Claude Code

Para una pregunta puntual sin contexto de repo ("¿cuál es la sintaxis de ARRAY_AGG en BigQuery?"), un chat común alcanza y es más barato — no hace falta que abra el proyecto ni use herramientas. Reservar Claude Code para tareas donde el valor está justamente en que puede leer, ejecutar y verificar contra el proyecto real.

Monitorear

/status muestra el modelo activo y el estado de la cuenta durante la sesión. Con salida en JSON (--output-format json), cada corrida en modo headless devuelve el costo exacto de esa invocación — útil para llevar el gasto de un job automatizado que corre todas las noches.
